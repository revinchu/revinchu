# 99. 행 삽입 성능과 F4 반복

## 문제와 기준

기준 커밋은 `b7ced1f13e40da1344922fd5d15072b2f91d9df8`이다. 사용자는 동아사이언스 보고서에서 행 삽입 시 정지하는 느낌과 F4 반복 누락을 보고했다. 원본과 저장본을 덮어쓰지 않고 D:의 비공개 진단 폴더에서 확인했다. 회사 원본과 진단 출력은 Git에 포함하지 않는다.

원본의 `DA_소재별`은 실제 저장 셀 2,739개와 수식 7개다. 전체 통합 문서는 실제 저장 셀 약 222만 개와 수식 18,380개이고, 빈 서식 셀까지 펼친 논리 셀 수는 이보다 크다. 작은 보고서 시트에 삽입해도 원본 전체를 여러 번 검사한 것이 지연의 주원인이었다.

기준의 Node 행 삽입 4회는 920~962ms였다. `sheetDeps()` 두 번 재구축이 약 609~665ms, `rewriteHyperlinks()`의 전체 셀 순회가 약 274~291ms였다. 실제 브라우저에서 32행 머리글 선택 → 리본의 시트 행 삽입 → F4 두 번은 표시까지 1,022~1,061ms였다. 선택 행은 유지됐지만 첫 화면의 `arrayCandidates()`도 전체 원본을 검사하고, 구조 명령과 변경 알림이 각각 화면을 갱신했다.

## 변경

- `CellMap`에 수식과 셀 링크 후보를 별도로 보관한다. 가져오기 전 `raw` 수식도 후보로 잡고 정규화 후 `formula` 플래그를 확인한다. 교체·삭제·빈 셀 구간 덮어쓰기·정규화·초기화에서 함께 갱신한다. 빈 셀 압축과 셀 값 저장 형식은 유지한다.
- 의존관계·내부 링크·구조 수식 갱신·저장 계산값 폐기·배열 수식 후보 검색은 해당 후보만 방문한다. 기존 계산 무효화와 실행 취소 규칙을 유지한다.
- 구조 명령은 변경 알림이 이미 예약한 화면 갱신을 사용한다. 같은 키 이벤트에서 격자와 개체 DOM을 두 번 그리지 않는다.
- 편집하지 않는 셀 에디터·격자·리본의 일반 F4는 문서 capture 경로에서 한 번 처리한다. `code=F4`가 있으면 비편집 상태의 `Process/229` 또는 `Unidentified` 보고에도 마지막 작업을 반복한다. 실제 글자 조합 중, 셀 수식 편집, 대화상자·메뉴·일반 입력칸에서는 반복을 실행하지 않는다. 수식 편집의 참조 전환은 기존 경로에 맡긴다.

## F4 재현 범위

기준에서 일반 F4는 실제 파일과 여러 초점에서 정상 실행됐다. 사용자의 물리 키보드에서 전달된 이벤트를 직접 캡처한 것은 아니다. 합성 이벤트의 `Process/keyCode229 + codeF4` 비편집 경로는 기준에서 실패했고 수정판에서 통과했다. 이 조건을 사용자 장치의 확정 원인으로 단정하지 않는다.

`tools/row-insert-performance-ui.mjs`는 실제 행 머리글과 리본을 이용해 19개 경우를 검사한다. 셀·격자·리본·시트 탭 초점, 연속 입력, 바쁜 작업 중 대기한 키, Alt 리본 경로, 수식 편집, 한글 조합 입력, 일반 입력칸 격리와 선택 유지가 포함된다. 원본 업무 파일을 열지 않고 공개 실행에서도 문서 API 쓰기와 외부 요청을 차단한다.

## 실제 원본 Node 비교

같은 파일·같은 시트의 48행 위에 삽입한 계측이다. 첫 삽입은 955.6 → 59.7ms, 다음 세 번은 932.6/962.2/919.7 → 31.3/31.4/24.5ms였다. 첫 작업은 약 16배, 반복은 약 30~38배 빨라졌다. 이는 순수 모델 시간이며 실제 화면 표시·사용자 하드웨어의 시간과 구분한다. 원본 SHA-256·파일 크기·수정 시간은 같았다.

의존관계 첫 구축도 296.9 → 7.7ms였다. `DepGraph.steps()`는 후보를 열별로 모은 뒤 기존 열 순서와 행 정렬을 유지해 같은 수식 run 묶음을 만든다. 후보 인덱스에 일반 값·압축 빈 셀을 복사하지 않는다.

## 실제 원본 화면과 연속 삽입

원본 `DA_소재별`의 32행 머리글을 선택해 리본으로 1회, F4로 2회 삽입했다. 브라우저 입력부터 두 animation frame 뒤 표시 확인까지 같은 측정법으로 비교했다.

| 동작 | 기준 | 수정판 |
|---|---:|---:|
| 리본의 시트 행 삽입 | 1,060ms | 154ms |
| F4 첫 반복 | 1,022ms | 105ms |
| F4 다음 반복 | 1,061ms | 111ms |

F4 표시 시간 평균은 1,041.5 → 108ms로 약 90% 감소했다. 이 컴퓨터의 Chromium 자동화 계측이며 Excel 자체 처리 시간이나 모든 문서의 성능을 보장하는 수치는 아니다.

이후 대기열에 실제 브라우저 프로토콜 F4 입력 8개를 추가해 총 11행이 정확히 삽입되는 것을 확인했다. 같은 행 선택을 유지하고 Undo 11회·Redo 11회를 실행했다. 피벗 12개, 필터 버튼 41개, 그림 20개를 포함한 전체 개체 43개의 위치·크기 및 셀 값·수동 서식 복원이 통과했다. 조작 직후 화면 갱신은 1회이며 배열 수식 후보 검색은 0.6~1.9ms로 줄었다. 대기열 검사에는 의도한 대기 시간이 포함되므로 그 전체 wall time을 순수 삽입 성능으로 인용하지 않는다.

- `package.json`의 test 명령과 동일한 `node --test test/*.test.js`: 2,291/2,291 통과. 이 셸에 npm 실행 파일이 없어 Node로 직접 실행했다.
- 신규 후보 인덱스 검사 15개: 수식/텍스트 정규화, 셀 링크, 빈 셀 구간 덮어쓰기, 부분 이동, 이름·표 참조, Undo/Redo, JSON/XLSX/prepared 저장 복원, 관계 없는 값 셀 전체 순회 금지.

- compiled smoke: 리본 명령 397개, bad 0.
- 후보 저장소·계산·의존 그래프 변경의 독립 읽기 리뷰에서 추가 결함 없음.

## 실제 원본과 저장본의 호환 비교

`tools/check.mjs`(수식 및 저장→재읽기)와 `tools/pvcmp.mjs`(파일의 Excel 저장 결과와 브라우저 피벗)를 원본·DDDD 저장본에 각각 실행했다. 현재 작업 기준 `b7ced1f`의 검사 로그는 직전 작업의 최종 after 기록이며, 그 작업의 earlier baseline `316020f`와 혼동하지 않도록 새 비공개 summary의 `beforeIdentity`에 구분했다.

| 파일 | 수식 차이 기준→수정판 | 저장 왕복 차이 기준→수정판 | 피벗 차이 기준→수정판 |
|---|---:|---:|---:|
| 원본 | 0→0 | 1→1 | 0/19→0/19 |
| DDDD 저장본 | 0→0 | 0→0 | 9/19→9/19 |

원본의 기존 SA_피벗 filter 속성 차이 1건과 저장본의 기존 피벗 차이 9건은 이 변경에서 늘어나지 않았다. 수식·왕복 상세 로그는 실행 시간만 제외하면 동일하고 두 피벗 로그는 바이트 단위로 동일하다. 두 파일의 SHA-256·크기·수정 시간과 검사 전후 생산 소스 hash도 일치한다. 현재 작업으로 기존 저장본을 자동 복구하거나 원본을 덮어쓰지 않았다.

자세한 타이밍·입력 trace·로그·스크린샷·파일 fingerprint는 Git에서 제외되는 `.local/row-insert-performance`에 보관한다. 개발 서버와 테스트 브라우저는 검증 후 종료하며 모든 작업 출력·캐시·임시는 D:를 사용했다.
