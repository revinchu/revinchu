# 11개 파일 저장 안정성 보강

## 범위와 판정

2026-10-04 제공된 XLSX 9개·XLSB 2개의 원본을 읽기 전용으로 확인하고, D:의 해시 일치 사본으로 검사한다. 압축 파일 합계 345,277,119바이트, 원본 시트 142개·피벗 113개·차트 120개·표 24개, 가져온 수식 12,594,746개다. 가져오기 성공과 전체 수식 재계산 성공을 구분한다.

파일별 원본 경로·내용·상세 결과는 로컬 검수 보고서에만 보관한다. 저장소·공개 배포에는 업무 검체를 넣지 않는다. 실제 파일 저장은 편집 마커와 기존 값·서식·옵션 표본을 비교하고, 독립 프로세스의 위셀 재열기와 Excel의 일반 읽기 전용 Open을 각각 기록한다. Excel의 복구 모드를 정상 열기로 세지 않는다.

## 확인한 원인과 수정

### 브라우저 자동 보관의 순간 메모리 증가

기존 v4는 한 시트의 압축 셀 조각을 모두 모은 뒤 하나의 IndexedDB 레코드로 썼고, 피벗 캐시는 전체를 structured-clone했다. v5는 압축 셀 조각·열 배열·문자열 사전·피벗 캐시·과거 항목 목록을 개별 레코드에 순서대로 쓴다. 형식화 배열은 최대 1MiB씩, 일반 배열은 최대 2,048개 및 추정 1MiB씩 나눈다. 단일 거대 값은 예외로 온전히 저장한다. sharedTypes·표시 형식 등 메타데이터와 복원한 최종 모델 전체까지 1MiB로 제한한다는 의미는 아니다.

자동 보관도 변경되지 않은 서식을 참조해 동기 JSON을 생성하므로 셀마다 서식 사본을 만들지 않는다. 압축 전 입력 Blob을 별도로 생성하지 않고 UTF-8 바이트를 압축 스트림에 직접 넣는다. 출력 Blob과 이전 저장 형식의 읽기 호환성은 유지한다. 큰 한글·이모지 셀, 압축 미지원 fallback, 압축 읽기/쓰기 실패와 기존 세대 보존을 검사했다. Chromium의 [Blob 저장 설계 문서](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/storage/browser/blob/README.md)는 빠른 Blob 생성의 전송 대기가 메모리 부담이 될 수 있음을 설명한다. 이는 변경 방향의 근거이며 해당 검체의 원인 확정과 실제 메모리 감소는 별도 실측으로 판단한다.

저장 중 변경 감시는 전체 메타데이터 JSON 문자열을 따로 보유하거나 검증마다 시트 메타를 다시 복제하지 않고, JSON과 같은 데이터 비교 규칙으로 확인한다. 셀 저장 순회도 정렬용 전체 배열 없이 기존 행 구간과 지점을 순서대로 읽는 경로를 사용한다. 이 변경 번들 `wixel-466f09b34f49afe7.js`에서 실제 대형 검체는 43시트·v5 manifest 저장을 45.39초, 최대 RSS 2,630,725,632B(2.45GiB)에 완료했다. 동일 3GiB 보호선으로 이전 시도는 저장 중 중단됐지만 이 시도는 저장을 완료했다. 새 페이지 복원은 34.21초에 별도 보호 중단되어 저장과 복원을 구분했다.

후속 복원 경로는 새로 읽은 IDB 청크를 곧바로 계산용 셀로 준비한다. 모든 원시 셀을 모은 뒤 다시 객체를 만드는 피크를 줄이기 위한 변경이다. WeakMap 소유권으로 표시한 입력만 통합문서가 단회 인수하며, 날짜체계·시트/셀·블록 정체성을 먼저 확인한다. 외부 JSON과 기본 API는 기존 복원 경로를 유지한다. 준비 입력 재사용/복사/오염은 명시적으로 거부하고, 같은 저장본을 각각 새로 읽은 문서는 독립적이다. 관련 저장 회귀 54개에서 날짜체계·배열 및 오래된 캐시·서식·주석·블록·편집/실행취소·재저장·이전 v2/v3/v4 복원을 확인했다. 이 후속 변경의 실제 대형 복원 결과는 별도로 측정한다.

복원 시 JSON 파싱이 같은 수식의 문자열 저장 공간을 반복 생성하는 문제도 확인했다. 대형 검체의 수식 4,697,882개 중 시트별 최초 16,384개·UTF-16 2Mi 문자 예산으로 정확히 같은 수식 문자열만 공유하면 4,634,150번의 중복을 피할 수 있다. 별도 저장본 스트림 분석의 중복 원시 문자열 크기는 953,098,909B였다. 이는 문자열 내용의 합계이며 실제 브라우저 RSS 절감량은 별도 실측한다. 기본/준비 IDB 복원과 WIXEL v2 읽기에 같은 제한을 적용한다. 문자열을 변경하거나 셀·주석·캐시 결과·AST 좌표를 공유하지 않으며, 예산을 넘는 단일 큰 값도 그대로 보존한다. 시트 또는 셀 프레임 종료 시 임시 Map을 비운다. 관련 82개 회귀가 통과했다.

최종 6bec 번들에서는 같은 실제 파일의 열기→셀 편집→v5 자동 보관→이전 페이지 폐기→새 페이지 복원→전체 대조 455/455판정이 통과했다. 논리 저장 셀 6,223,236개·수식 4,697,881개, 모든 열 블록·과거 항목 및 43개 시트 메타데이터/피벗 필드 서식을 확인했다. 기존 지문과 다른 작은 시트 다섯 개는 같은 내용의 빈 셀 구간이 138개 합쳐진 표현 차이였다. 같은 브라우저 실행의 저장 직전 지문을 이전 기준에 연결한 뒤 81,242개 좌표의 raw·수식·서식·cached 값을 펼쳐 비교해 모두 일치했다. 나머지 38개 시트는 기존 구간 지문과 동일했다. 다른 import 실행끼리 메타 해시가 달랐던 21개 시트는 임의 생성 table/slicer ID가 있는 시트 집합과 정확히 일치했으며, 이번 동일 문서의 저장 전후 메타는 ID까지 전부 같았다.

최종 실행의 열기 73.298초, 자동 저장 101.980초, 새 페이지 복원 101.773초, 전체 지문 23.378초였다. 저장 최대 RSS 2,104,111,104B(1.960GiB), 복원 1,663,094,784B(1.549GiB), 전체 검사 2,625,056,768B(2.445GiB)로 동일한 프로세스 트리 3GiB/시스템 여유 1.25GiB 보호선을 통과했다. 강제 GC나 보호선 상향은 사용하지 않았다. 바로 전 동일 번들 실행은 저장43.167초/복원39.928초였으므로 이 시간을 섞어 성능 향상률을 만들지 않는다. 앞선 보호 중단과 비교 도구의 표현 차이 실패는 별도 이력으로 보존했다. 이 검사의 논리 저장 셀 수는 다른 검수의 열 블록 포함 업무 내용 셀 수와 집계 범위가 다르다.

본문은 불변 세대 참조로 저장하고 마지막 manifest만 CAS로 확정한다. 취소·디스크 용량 오류·문서 전환·다른 탭의 충돌에서는 기존 완전한 세대를 보존한다. 숨김 등 시트 상태만 바뀌면 본문을 재사용하며, GC는 현재 manifest가 참조하는 청크를 지우지 않는다. v2/v3/v4 읽기를 유지한다. 과거 피벗 항목만 큰 문서도 localStorage 한도를 검사해 IndexedDB로 보낸다.

### 파일 저장 취소와 진행 창

XLSX·WIXEL·CSV 등을 저장하는 진행 창에 취소 버튼을 추가했다. 준비·생성·쓰기의 같은 AbortSignal을 연결하고, 멈춘 스트림 read나 비동기 iterator를 기다릴 때도 취소를 받아 임시 쓰기를 폐기한다. 실제 파일 close가 시작되면 취소 버튼을 비활성화하고 완료 결과를 기다려 확정된 저장을 취소했다고 잘못 표시하지 않는다. 오류나 취소 후 문서 이름을 바꾸거나 자동 다운로드로 우회하지 않는다. 직접 쓰기는 ZIP 입력 청크에서도 취소를 확인하지만, Blob XLSX 다운로드는 압축 항목 경계에서 협력적으로 취소하므로 한 항목을 압축하는 중 즉시 종료되는 것은 아니다.

390×844 화면에서도 진행 창과 취소 버튼의 겹침 없이 클릭·취소가 동작함을 확인했다. 이 검사는 데스크톱 Chromium의 작은 viewport이며 iPad 실기 검사가 아니다.

### 피벗 과거 선택 항목 소실

XLSX 캐시를 현재 레코드에서 재생성하면서 레코드에 없는 과거 sharedItems가 사라졌다. 이제 캐시별 원본 항목과 자료형을 통합문서에서 한 번만 공유 보관하고, 원래 번호를 유지한 채 새 값만 뒤에 추가한다. 동일 범위라도 서로 독립된 캐시는 합치지 않는다. 사용자가 명시적으로 연결한 슬라이서 보고서는 같은 원본·같은 레코드인 캐시만 과거 항목을 합쳐 저장한다. 서로 다른 레코드의 캐시는 조용히 한쪽으로 대체하지 않고 새로 고침이 필요한 이유를 알린다. 피벗마다 원본 배열을 복제하지 않으며 WIXEL·JSON Blob·분할 자동 보관에도 연결했다.

이전 실제 검체에서는 월 2→1, 일별 153→31, 일 58→31로 줄던 선택이 각각 2→2, 153→153, 58→58로 유지됐다. 이는 위셀 모델 재열기 결과다. 선택 배열/객체 키의 순서와 실제 필터 선택 집합, UI 정렬 순서를 구분해 판정한다. 추가 Excel 대조에서 날짜 캐시의 <d>가 <n>으로 바뀌는 문제를 발견해, 날짜 항목 유형·표시 형식을 별도로 보존하도록 수정했다. 1900/1904 날짜체계·밀리초·날짜와 숫자의 혼합·삭제 정책·캐시 연결·분할 자동 보관을 회귀 검사했다. sharedItems 목록 없이 cacheRecords에 날짜만 있는 필드도 날짜 전용 메타를 보존한다.

별도의 이전 대형 회귀 검체(이번 11개와 별개)는 최종 WIXEL 재열기 5,843판정 통과, XLSX는 선택 배열/객체 키 순서만 다른 6건 외 내용 차이가 없었다. 41시트·13피벗을 보존하고 4개 캐시 필드의 날짜 <d> 항목 912개를 확인했다. 실제 Excel16 build14334의 기본 일반 Open과 구조 조회에서 원본과 생성본 24개 필터의 항목 이름·개수·개별 Visible 및 선택 집합이 모두 일치했다. 필터가 있는 8개 시트만 native 세부 보고서에 기록했으며, 통합문서 전체 시트 수와 구분한다.

### 피벗 필드 자체의 숫자 표시 형식

날짜 항목 유형을 보존한 뒤 실제 Excel에서 추가 대조하자 한 파일의 날짜 필드 14개가 yyyy-mm-dd에서 표준으로 바뀌었다. 캐시 필드의 형식, 값 집계의 형식, 각 피벗 필드의 numFmtId는 서로 다른 설정이다. 이제 각 피벗의 fieldNumberFormats에 명시적인 General·내장 ID·사용자 지정 코드를 각각 보존한다. XLSX 저장 시 내장 ID를 유지하고 사용자 코드는 스타일 풀에 정확히 등록한다. 같은 캐시를 쓰는 피벗도 서로 다른 필드 서식을 유지하며, 사용자 코드로 덮어쓴 내장 번호도 우선한다. 동기/Blob XLSX와 WIXEL/JSON 왕복의 신규 5개 회귀를 확인했다. 이번 검체 중 세 파일에 변경 영향이 있다. 최신 재저장본의 실제 Excel 조회에서 N02 39개·N06 144개 필드의 NumberFormat·자료형·항목 수·배치가 원본과 일치했다. N02의 표시 표본도 모두 같았다. N06은 41개 필드의 native 표시 표본이 달랐다. 원본 XLSB BIFF와 생성 XLSX를 독립 비교한 결과 이 41개 모두 자료형을 포함한 캐시 값 집합·캐시 순서 및 피벗 항목 집합이 동일해 항목 누락은 없었다. 그중 16개의 XML 피벗 항목 순서 차이는 독립적으로 확인했다. 날짜 필드 35개의 SourceName 표본은 같지만 Name/Caption 표시가 달랐으며 원인은 확정하지 않았다. 날짜 표시 후보의 해시 역매핑은 서로 다른 날짜가 같은 표시가 되는 경우를 배제하지 못하므로 native 열거 순서의 증거로 사용하지 않는다. XML 순서가 같은 숫자 필드 두 개의 표본 차이도 원인 미확정이다. 이를 모든 표시 동등성 통과로 세지 않는다. N01/P04의 이전 날짜 표시 결과를 이번 숫자 서식 수정으로 모두 해소했다고 갱신하지 않는다.

### 확장자가 .bin인 EMF 그림

실제 검체의 image/unknown 파일이 EMF 서명을 가지고 있어도 확장자만 검사해 그림을 버렸다. 지원 MIME을 알 수 없을 때 기존 isEmf 서명 검사로 확인해 화면용 SVG를 생성하고 저장에는 원본 EMF 바이트를 보존한다. 합성 .emf/.bin 왕복 회귀를 추가했다.

### 그림 그룹 저장 중복과 축소된 그룹

그룹 메타데이터에 원본 base64 그림을 넣어 중첩 그룹마다 중복 저장하던 경로를 바꿨다. 편집용 원본도 실제 XLSX 미디어 관계로 저장하고, 같은 원본은 시트를 넘어 한 파일로 공유한다. 그림·원본·보정 옵션은 유지한다. 기존 인라인 메타데이터를 계속 읽으며, Excel이 관계 번호를 바꾼 경우와 메타데이터 관계가 누락된 경우의 표준 그룹 복원을 검사했다.

높이 또는 너비가 0인 원본 Excel 그룹을 해체하던 조건도 수정했다. 부모 크기 0과 양수 자식 좌표계를 함께 보존해 다음 저장에서 그룹 구조와 개체 수가 달라지지 않게 했다.

### 피벗 항목 보존 옵션과 제목

자동·없음·최대·사용자 지정 missingItemsLimit를 XLSX/XLSB에서 가져와 옵션창과 저장에 연결했다. 기존 '없음' 캐시라도 새로 고침 전의 과거 항목 선택은 스타일 저장만으로 삭제하지 않는다. 보존 정책을 '없음'으로 바꾸거나, '없음' 상태에서 원본을 새로 고친 경우에 제거 정책을 적용한다. 양수 한도는 OOXML 옵션으로 보존하며, 위셀 자체에서 해당 개수에 맞춰 과거 항목을 가지치기하는 기능까지 구현한 것은 아니다.

행 필드가 하나인 테이블/개요형 피벗의 명시적 rowHeaderCaption을 적용한다. 기존 데이터 필드 이름을 대신 표시해 제목 앞 공백이 사라지던 실제 검체를 회귀 기준으로 삼았다.

### 필터 결과가 빈 피벗의 Excel 열기 실패

실제 검체 한 개의 생성 XLSX는 위셀 재열기와 전체 내용 지문이 일치했지만 Excel 일반 Open에서 오류 1004가 재현됐다. Open XML SDK 2.20의 Office2021 메타데이터 검사에서 피벗 하나의 rowItems가 count=0이고 필수 자식 i가 없는 오류를 확인했다. 해당 목록이 비어 있으면 선택·필드·캐시·셀을 보존하면서 선택 요소인 rowItems/colItems 자체를 생략한다. 행/열 방향과 동기/Blob 출력의 네 회귀에서 과거 항목 선택, 빈 결과, 총합계 옵션의 왕복이 통과했다. 이번 11개 이전 생성본 중 이 잘못된 빈 목록은 해당 파일 한 파트에만 있었다.

601MB의 큰 시트 본문을 제거한 별도 진단 사본도 같은 오류여서 시트 크기를 원인으로 단정하지 않았다. 최신 제품 코드로 모든 내용을 다시 저장한 47,324,754B 파일은 CorruptLoad=0의 Excel 일반 Open에서 정상 열렸고, 정확한 FullName·ReadOnly·19개 시트와 편집 표식, 내용/구조 차이 0을 확인했다. Open 85.413초, 전체 검사 98.72초, Excel 최대 RSS 1,487,556,608B였다. 이전 저장본과 워크시트 19개 등 284개 ZIP 파트가 바이트 단위로 같았다. 빈 rowItems 제거, 수정 시각, 별도 대응표로 확인한 그림 그룹 생성 ID만 달랐으며 본문을 줄여서 통과시킨 검사가 아니다. SDK 규격 검사와 실제 Excel 열기 결과를 함께 기록한다.

### 실제 Excel 검사 도구의 판정 정정

Excel Workbook에는 RepairMode 속성이 없다. 초기 검사 도구에서 없는 속성의 null을 false로 변환한 값은 복구하지 않았다는 독립 근거로 사용할 수 없다. 이전 일반 Open 뒤 실제 시트·내용 조회 성공은 유지하되 이 잘못된 속성 판정은 제외한다. 후속 검사는 Workbooks.Open의 CorruptLoad=0을 명시하고, 반환된 동일 통합문서의 시트 수·ReadOnly=true·예상 FullName 및 내용·구조 조회를 확인한다. 존재하지 않는 속성을 기다린 한 진단의 시간 초과도 제품 실패와 분리한다. 근거는 [Excel Workbook API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.excel._workbook?view=excel-pia), [Workbooks.Open](https://learn.microsoft.com/en-us/office/vba/api/excel.workbooks.open), 설치된 Excel interop 메타데이터 확인이다.

## 검사 및 후속 기준

- 최종 번들 6bec에 대응하는 전체 Node 단위 1,827개가 통과했다(47.675초, test-concurrency=2, 실패·건너뜀 0). 날짜·숫자 표시 형식, 필터 UI, 자동 보관과 복원, 정확한 수식 문자열 공유, 빈 피벗 목록 수정을 포함한다. 새 취소·할당량·CAS·부분 누락·GC·이전 형식 복원 회귀를 포함한다.
- 최종 6bec 번들 UI: 저장 대화상자 20/20(69.297초/최대RSS 1,203,355,648B), 리본 명령 호출 387개 bad 0(70.469초/643,371,008B), 피벗 과거 선택 UI 5사례·27판정(7.281초/506,867,712B)이 통과했다. 가상 File System Access API와 격리 Chromium을 사용했으며 실제 OS 선택창·권한 UI까지 검사한 것은 아니다. 최종 일반/Cloudflare 빌드와 Wrangler dry-run도 성공했다.
- 자동 보관 후속 변경 전 Cloudflare 번들 `wixel-7316fdaf1a6127bd.js`에서 저장 UI 20개 및 리본 명령 387개를 검사해 실패 0이었다. 각각 61.53초/최대 1,419,292,672B와 68.27초/최대 627,814,400B였다. 최초 이전 검사에 설정한 1GiB 프로세스 트리 한도는 보호 중단되었으며, 표준 3GiB에서 정상 완료했다. 보호 중단은 브라우저 자체 크래시와 구분한다. 일반/Cloudflare 빌드 및 Wrangler dry-run도 성공했다.
- 소형 실제 4개 파일의 check.mjs 수정 전후: 수식 2,951개 재계산 차이 0, 저장 왕복 문제 0.
- 11개 모두 WIXEL·XLSX 저장 후 독립 프로세스의 전체 내용 지문이 일치했다. 생성 XLSX 11개 모두 실제 Excel 일반 Open 및 편집 표식 확인을 완료했다. 원본 업무 내용 셀 38,173,011개·수식 셀 12,594,746개이며 검사 표식과 외부링크 캐시 시트를 제외한 값·수식·보관된 계산값 보존 검사다. N03의 인쇄 여백 한 곳과 N04 두 곳에 소수4자리 인치 반올림 차이(최대 약0.001mm)가 남아 엄격 서식 검사를 전부 통과했다고 표현하지 않는다. 작은 실제 4개 파일의 13개 시트에서는 CSV 10,155셀·HTML 9,199셀 및 개체 16개를 독립 파서로 검증해 값 차이 0이었다.
- 대형 실제 시트 전체 362,095행×22열의 CSV와 HTML을 순차 스트림으로 저장하고 독립 파서로 각각 7,966,090셀을 전수 대조해 차이 0(7판정)을 확인했다. CSV 64,789,866B/13.182초, HTML 1,690,167,603B/232.239초·1,449구간이었다. Node 최대 RSS 2,114,334,720B, 독립 파서는 약32.05MB였다. 원본·범위·제품 API를 축소하지 않았다. 큰 HTML을 모바일에서 실제로 열어 조작하는 사용성까지 검사한 결과는 아니다.
- 실제 그림 중심 검체의 XLSX 출력은 147,139,595바이트에서 86,836,925바이트로 줄었고, 원본 미디어 349개 전부 해시가 일치했다. Excel 정상 Open에서 도형 421개·표본 내용·편집 표식이 일치했다.
- 실제 5개 피벗의 브라우저 표시 비교는 제목 수정 전 1곳 차이에서 수정 후 0곳으로 바뀌었다.
- 작은 실제 파일 네 종류를 순차 5회 전환하고 늦은 이전 파일 읽기 응답을 주입한 브라우저 검사 31단계·133판정이 통과했다. 최종 준비 복원 경로를 포함한 최신 소스에서 다시 통과했으며 76.765초, 최대 RSS 810,008,576B였다. 셀 편집·실행 취소·다시 실행·저장·새 페이지 복원을 확인했고 페이지 오류와 외부 요청은 0이었다. Chromium의 iPad형 에뮬레이션이며 Safari 실기 결과는 아니다.
- 자동 행 높이 네 곳은 Excel 재측정과 2~19px 차이가 확인됐다. 원본 customHeight가 없는 자동 높이이며 저장 왕복 손실과 별도 판정한다.
- 선택의 파일 보존·명시적 보고서 연결·항목 보존 정책 개선을 모든 피벗 옵션의 Excel 동등성으로 표현하지 않는다. 날짜 캐시 표시 형식의 네이티브 Excel 재검사도 별도로 기록한다.
- 편집 모델 전체는 여전히 메모리에 올라온다. Safari의 대형 Blob 다운로드 제한, 물리 iPad RAM·키보드·마우스 동작, 임의 1~20GB 통합문서의 전체 기능을 이번 검사로 보장하지 않는다. 후속 설계는 77 문서의 구간 읽기·디스크 본문·수식 압축·구간 출력 순서를 따른다.


## 피벗 필터 UI의 과거 선택 보존

파일 내 선택 보존을 검증한 뒤, 현재 레코드에 없는 과거 항목을 UI 항목 목록에서 빼는 경로를 추가로 발견했다. 피벗 필터 창의 초기 선택이 목록 밖 값을 제거하면서, 현재 31개·기존 선택 153개인 경우 확인만 눌러도 선택이 31개로 축소되거나 필터가 해제될 수 있었다. 슬라이서 Ctrl 다중 선택 역시 보이는 항목으로만 선택을 재구성했다. 공용 표 필터의 미지 값 정책을 바꾸지 않고 피벗 전용 항목 모델을 연결했다. 현재 레코드·보존 캐시·명시 선택을 함께 구성하며, 변경 없는 확인은 원래 선택 배열을 유지한다. 슬라이서의 삭제 항목/무데이터 숨김은 표시만 바꾸고 Ctrl 선택 시 보이지 않는 기존 선택도 유지한다. 직접 단일 선택·명시적 필터 해제는 기존 의도대로 적용한다. 날짜 유형·1904 날짜체계·그룹 필드·사용자가 바꾼 항목 캡션을 표시하고, 보고서 필터의 단일/다중 모드만 바꾼 경우도 저장한다.

신규 합성 UI 5사례·27판정, 기존 피벗 필터 29사례·181판정, 슬라이서 Ctrl 1사례·8판정이 통과했다. 페이지 오류·외부 요청·쓰기 요청은 0이었다. 현재 31개/선택 153개/보존 275개, 캐시 메타 없는 선택, 검색 추가, 단일 선택/해제, 숨김/삭제 표시를 포함한다. 기존 텍스트 기반 필터 스키마에서 숫자 1과 문자 "1"을 독립적으로 선택하지 못하는 한계는 이 UI 수정으로 해결한 범위가 아니다.
