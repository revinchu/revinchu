# 로컬 대용량 저장과 19개 파일 검수

## 목표와 합격 기준

원본을 읽기 전용으로 열고, 편집한 사본을 저장한 뒤 위셀과 실제 Excel에서 재열어 확인한다. 파일이 만들어졌다는 사실, ZIP CRC 통과, 위셀 재열기, 실제 Excel 열기를 서로 다른 검증 단계로 기록한다. 원본 파일·셀 내용·검사 결과의 비공개 데이터는 저장소나 공개 서버에 올리지 않는다.

이번 19개 원본의 압축 크기는 총 627.7MB, 압축 해제 크기는 약8.86GB다. 시트439개·피벗346개·차트364개·표89개·슬라이서 캐시134개가 포함된다. 파일 크기만으로 모바일 메모리 요구량을 판단하지 않는다. 개별 이름·결과는 로컬 검수 보고서에 보관한다.

## 구현

- `file-save.js`: 사용자 동작 중 선택한 File System Access handle에 최대1MiB씩 기록한다. 작은 조각은 하나의 제한된 버퍼로 합친다. 문서 버전·취소·동시 쓰기를 검사하며 실패 시 abort한다. 모든 쓰기 뒤 마지막 검사를 통과해야 close로 확정한다. native seek가 있으면 버퍼를 먼저 비우고 이미 쓴 범위 안에서만 이동하며, 최종 파일 크기에 덮어쓴 바이트를 중복 집계하지 않는다.
- `wixel-file.js`: 레코드/압축 ReadableStream을 파일 대상으로 바로 전달한다. 기존 Blob API와 이전 WIXEL 읽기 호환은 유지한다.
- `xlsx.js`, `zip-stream.js`, `zip-records.js`: 시트·셀·피벗 캐시를 순차 생성하고 압축 결과를 즉시 sink에 보낸다. native seek가 있으면 본문을 저장한 후 local header의 CRC·크기를 보정한다. 작은 파일은 ZIP32를 쓰며, 실제 크기·위치·항목 수가 넘을 때만 ZIP64가 필요하다. seek 미지원 경로는 ZIP32 한도 초과를 오류로 처리해 손상 파일을 확정하지 않는다. ZIP64 읽기는 별도 helper로 추가하고 기존 ZIP32 경로를 보존한다.
- `csv.js`: 행을 지연 생성하고 UTF-8 바이트를 나누어 출력한다. 큰 인용 필드, CR, 따옴표와 유니코드 surrogate 경계를 보존한다.
- `html-export.js`: 기존 인쇄 페이지와 독립된 HTML 출력을 디스크 sink에도 연결한다. 전체 HTML Blob을 보관하지 않고 제한된 표시 구간을 기록한다.
- `xlsx.js` 가져오기: 기존5만 행 기준에 8,192행 이상·262,144셀 이상인 넓은 시트를 추가해 값 셀을 열 블록에 담는다. 새 경로에서는 @텍스트 셀을 일반 셀로 남겨 입력창 원문을 보존한다. 저장된 사용 범위만 큰 희소 보고서는 서식 열의 값·셀·명시적 빈 셀 구간에 구멍이 있는지 확인하고, 빈 곳에 서식이 번질 수 있으면 기존 셀 저장 방식으로 되돌린다. 검사할 때 전체 사용 범위의 행×열을 펼치지 않는다.
- `xlsb.js`: 수식 디코딩용 memo를 시트별로 나누고 16,384항목/2Mi UTF-16문자 예산을 적용한다. 시트 완료·취소 시 해제한다. 수식과 셀 데이터는 제거하지 않는다.
- `stylepresets.js`: Excel tint의 1/32767 정밀도와 정수 중간 계산을 반영한다. 384개 독립 Excel 색과 원시 XML 입력240개를 대조한다.
- `page.js`: 가져온 pageSetup에 paperSize가 없으면 Excel의 Letter 기본값을 적용한다. 새 위셀 문서의 A4 기본값은 유지한다.
- ODS 저장에서 실제로 포함하지 않는 개체·피벗·조건부 서식 등이 있으면 저장 범위를 확인하게 한다. 이 형식의 전체 충실도를 구현한 것으로 표시하지 않는다.

## Excel 컨테이너 호환에서 발견한 문제

강제 ZIP64 스트림은 표준 ZIP 해제·CRC·위셀 읽기를 통과했지만 Excel16 build14334의 정상 Open에서 실패했다. 동일 XML을 ZIP32로 포장하면 열렸고, Content_Types 순서는 결과에 영향을 주지 않았다. 작은 entry/local header를 확정하고 classic central/EOCD를 유지한 독립 prototype과 최종 JS 후보는 실제 Excel에서 정상적으로 열렸다. 일반 ZIP64 성공을 Excel 호환성의 증거로 삼지 않는다.

## 실제 대용량 쓰기 증거

| 검사 | 결과 | 의미 |

| 20GiB 원문 ZIP 압축·디스크 저장·전체 복원CRC | 통과, 274.12초/RSS62.92MiB | 출력은 약20MB이며 20GB 출력 시험과 구분 |

위 결과는 20GB Excel 문서를 모든 기기에서 열고 편집한다는 보장이 아니다. reader와 워크북 모델의 메모리, 계산 비용, 파일 형식 한계는 별도로 남는다.

## 남는 범위와 다음 설계

1. Safari/iPad에서 시스템 파일 저장 스트림 API가 없으면 기존 Blob 다운로드를 사용한다. 실제 iPad의 메모리 종료·Bluetooth 입력은 데스크톱 WebKit 검사와 구분한다.
2. 전체 압축 XLSX가4GiB를 넘을 때 실제 Excel 호환은 보장하지 않는다. 새 auto writer의 큰 ZIP 검증과 큰 Excel 편집 가능성은 다르다.
3. ODS는 현재 전체 문자열 ZIP32 경로이며 개체/피벗 등 보존도 제한된다. 별도 lazy 본문, 서식 사전 등록, 첫 mimetype 무압축 규칙을 검증한 뒤 확장해야 한다. CSV는 값, HTML은 표시 사본, PDF는 인쇄물이다.
4. 대량 반복 수식은 현재 셀 객체를 보관한다. 다음 단계는 반복 수식 템플릿+행 범위+값 배열 저장, 수정 셀만 독립 객체로 승격하는 구조다. 가져오기, 참조 이동, 계산, 실행 취소, 저장, 복구를 함께 검증해야 하므로 임의 셀 생략으로 메모리를 줄이지 않는다.
5. 기존5만 행 초과 블록 경로에서 @서식 숫자 문자열의 내부 작은따옴표가 수식 입력창에 노출되는 문제가 남는다. 새 면적 확장 경로에는 이 회귀가 발생하지 않도록 예외 처리했다.
6. 표본 값·직접 서식·옵션 비교를 모든 셀의 픽셀 및 모든 기능 동등성으로 확대 해석하지 않는다. OLAP/DAX 등 기존 비지원 기능은 별도 제한이다.

공식 참고: [Excel 사양과 제한](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits), [File System Writable](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemWritableFileStream), [OPC ZIP64 플래그](https://learn.microsoft.com/en-us/windows/win32/api/msopc/ne-msopc-opc_write_flags).

## 실파일 최종 보강 결과

- 19개 원본 모두 위셀 가져오기를 완료했다. 이전에 자원 보호로 중단했던 N07도 메모리 개선 후 가져오기 69.36초, 피크 RSS 2.03GiB, 최소 시스템 여유 2.43GiB로 완료했다. 모바일 하드웨어에서 측정한 결과는 아니다.
- 수정한 N08의 XLSX 사본을 실제 Excel에서 복구 모드 없이 정상 열었다. 9개 시트, 15개 피벗, 5개 슬라이서와 표·차트·도형 구조를 대조하고, 72개 표본 내용·수식에서 차이가 없음을 확인했다. 변경한 피벗·슬라이서 스타일, 셀 굵기·기울임·채우기도 확인했다.
- N08의 최종 배포 번들 브라우저 가져오기는 36.587초, 전체 검사는 42.426초였다. 슬라이서 우클릭에 셀 서식 메뉴가 없는지, 단일 선택, Ctrl로 정확히 두 항목 선택, 활성 필터의 실제 해제, 실행 취소 복원을 클릭으로 확인했다. 피벗 행 필터 검색, 현재 선택 추가 체크박스 표시, 적용, 실행 취소도 통과했다. 체크박스의 모든 조합 의미를 검증한 것은 아니다. 셀 편집과 실행 취소·다시 실행, 문서 유지가 통과했고 페이지 오류와 롤백은 없었다.
- 슬라이서 검사는 모델 좌표로 스크롤한 후 실제 클릭 가능한 항목을 찾았다. 원본 Excel 캐시의 과거·무데이터 항목까지 포함한 전체 목록 동등성은 별도 미검증이다.
- 실제 Excel 기준 수집은 17개 파일에서 완료했고 2개는 COM 호출 거절로 미완료다. 이 두 파일의 위셀 가져오기는 성공했다.
- N10·N14·N19에는 자동 행 높이 차이가 남는다. 원본은 customHeight=false와 이전 자동 높이를 저장하고, Excel은 열 때 글꼴을 다시 측정하지만 위셀은 저장 높이를 유지한다. 모든 화면 배치가 동일하다는 판정은 보류한다.

### 최종 서식 회귀와 재검 범위

N01과 N09의 희소 보고서에서 저장된 dimension이 실제 값보다 훨씬 컸다. 새 면적 기준으로 블록을 적용할 때 원래 없던 빈 셀에 열 서식이 적용되는 차이를 발견해 배포를 보류했다. 새 면적 경로는 원래 서식이 존재한 구간만으로 연속성이 입증될 때 블록을 유지하고, 그렇지 않으면 입력값과 명시적 빈 셀 서식을 셀 단위로 복원한다. 누락된 셀은 새로 만들지 않는다. 합성 회귀 검사는 기본 서식 초기화, 부분 서식, 행·열 서식, 명시적 빈 셀, 링크·메모와 재열기를 포함한다.

이 문제는 기존 5만 행 초과 블록 경로에서도 잠재적으로 발생할 수 있다. 이번 변경은 새 면적 경로의 회귀를 막는 범위로 제한했으며, 기존 경로의 전체 빈 셀 서식 동등성을 인증하지 않는다.

## 실제 20GB 통합문서를 위한 다음 구현 순서

아래 예산은 다음 개발의 목표값이다. 이번에 달성한 수치나 모든 브라우저에서 사용할 수 있다는 보장이 아니다. 새 외부 의존성이나 서버 업로드를 전제로 하지 않는다.

1. **구간 읽기 기반 가져오기.** `app.js`의 전체 `file.arrayBuffer()`와 `zip.js`의 전체 바이트 입력을 파일 구간 읽기로 바꾼다. `xlsx-row-stream.js`와 `xlsb.js`는 제한된 압축 청크 사이의 XML·바이너리 레코드를 이어 읽는다. 입력·압축 해제 버퍼 합계 목표는 64MiB다. 가장 큰 시트에 비례해 버퍼가 커지지 않고 CRC·경계·취소·이전 문서 보존을 통과해야 한다.
2. **디스크에 분할 저장한 워크북 본문.** `workbook.js`, `cellmap.js`, `block.js`를 메타데이터·수정분·읽기 캐시·디스크 본문으로 분리한다. `storage.js`의 IndexedDB를 확장하고 가능한 환경의 OPFS는 선택적으로 사용한다. 관리 캐시 목표는 데스크톱 512MiB, 태블릿 128MiB이며 브라우저 자체 메모리는 별도로 측정한다. 캐시 교체 전후 값·자료형·빈 셀·서식·개체 위치가 같아야 한다.
3. **반복 수식과 계산·실행 취소 압축.** 수식을 템플릿·상대참조 범위·계산값 배열로 표현하고 수정한 셀만 독립 객체로 승격한다. 의존성·AST 캐시에도 상한을 두고 실행 취소는 변경 기록을 저장한다. 반복 수식 100만 개의 입력·참조 이동·재계산·undo/redo가 일치해야 하며 취소된 계산의 부분 결과를 확정하면 안 된다.
4. **변경된 부분만 자동 저장.** `big-storage.js`의 불변 세대와 CAS manifest를 분할 본문으로 확장한다. `snapshot-blob.js`, `pivot-snapshot-storage.js`, `Workbook.serializeBlob()`의 전체 복사를 고정된 본문 참조와 변경분으로 대체한다. 추가 버퍼 목표는 32MiB다. 강제 종료·취소·용량 부족을 모든 단계에 주입해도 이전 또는 새 완전한 세대만 복구하고 다른 문서로 돌아가면 안 된다.
5. **분할 본문을 읽으며 출력.** `file-save.js`, `wixel-file.js`, `writeXlsxToSink()`에 디스크 본문 공급자를 연결하고 저장 도중 편집과 분리된 고정 세대를 읽는다. 전체 Blob·문자열 조립 없이 저장하며 성공 전 기존 파일을 보존해야 한다. 직접 출력 API가 없는 Safari의 단일 대용량 파일 출력은 별도 구현·실기 검증이 끝날 때까지 미달로 기록한다.
6. **실제 1GB→5GB→20GB 검체 검증.** 압축 크기·해제 크기·셀 수·수식 수를 각각 기록하고 가져오기→편집→자동 저장→종료·복구→파일 전환→내보내기→재열기를 수행한다. 모든 셀과 지원 개체·옵션을 순차 대조하고 취소·디스크 부족·탭 경합에서 손실과 문서 혼동이 없어야 한다. ZIP64 성공과 실제 Excel 재열기를 별도로 판정한다.

## 최종 19개 파일 재검 집계

마지막 희소 서식 수정까지 포함한 동일 소스로 19개 모두 다시 가져왔다. 검사 시작·종료의 소스 해시가 일치했고, 원본 439개 시트·346개 피벗·364개 차트·89개 표의 구성수가 모든 파일에서 일치했다. 가져오기 경고와 수식 구문 변환 오류는 0이다. 전체 수식 재계산까지 검증한 의미는 아니다.

실제 Excel 기준을 확보한 17개 파일에서 값·수식 표본 3,248개, 직접 서식 29,228개, 피벗·표 옵션 3,066개를 대조했고 차이는 0이었다. 보기·인쇄·치수 15,788개 중 자동 행 높이 158개(N10 55개, N14 55개, N19 48개)는 차이가 남았다. 나머지 두 파일은 Excel COM 기준 수집이 완료되지 않아 원본과의 직접 대조에 포함하지 않았다.

가져오기 시간은 파일별 3.584~69.358초, 최대 프로세스 RSS는 2.035GiB였다. 이는 데스크톱 Node 검사이며 물리 iPad의 속도·메모리 결과가 아니다. 19개 원본의 크기와 수정 시각은 검수 전후 같았다.

숫자 표시형식의 문자열 차이 303건은 동등 여부를 확정하지 못한 검토 항목이며, Excel COM에서 스타일명을 확보하지 못한 옵션 242건은 비교에서 제외했다. 이 항목들은 위의 차이 0 통과 수에 포함하지 않는다.
