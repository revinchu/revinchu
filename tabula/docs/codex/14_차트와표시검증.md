# 14. 차트·피벗 옵션·화면 표시 보강과 검증

이 문서는 2026-10-01 차트 종류 선택, 콤보 계열별 축, 피벗의 오류 값 표시 및 시트 눈금선·테두리 표시 작업과 합성 데이터로 확인한 범위를 기록합니다. 전체 단위 테스트·최종 빌드·공개 배포 결과는 통합 검증 뒤 별도로 기록하며, 아래의 부분 테스트 수를 더해 전체 테스트 수로 계산하지 않습니다.

## 차트 종류와 콤보 편집

기존에는 17개 차트 유형과 47개 갤러리 변형이 있었습니다. 이번에는 유형 수를 부풀리지 않고 기존 렌더링 결함을 고치고 실제 동작하는 변형 3개를 추가하여 **17개 유형, 50개 갤러리 변형**이 되었습니다. 3D 변형 12개는 이 갤러리 수에 포함됩니다.

- 추가 변형: 표식이 있는 100% 기준 누적 꺾은선형, 쪼개진 도넛형, 기본 축을 사용하는 세로 막대·꺾은선 콤보. 보조 축 콤보 견본과 구분됩니다.
- 여러 계열을 가진 도넛은 첫 계열만 그리던 문제를 수정하여 계열마다 별도 링을 표시합니다. 한 항목이 100%인 링도 다른 링을 가리지 않습니다.
- 차트 종류 변경 창에서 계열별 **세로 막대형·꺾은선형·영역형**과 **기본 축·보조 축**을 선택하고 즉시 미리 봅니다. 확인은 한 번의 실행 취소 이력으로 적용되며 취소는 원본을 바꾸지 않습니다.
- 범위가 없는 가져온 계열, 숨긴 계열의 원래 번호, 색·표식·레이블을 유지합니다. 보조 축에서 기본 축으로 돌아갈 때 `axis: 0`을 명시적으로 보존합니다.
- 콤보에서 일반 차트로 바꿀 때 계열별 종류·축 재정의를 제거하여 선택한 종류가 실제로 적용되게 했습니다. 기존 계열의 다른 서식은 유지합니다.

모델의 `seriesFmt[i].type`은 계열 종류, `axis: 0 | 1`은 기본 축·보조 축입니다. 가져온 `axis: 'secondary'` 또는 `'right'`는 계산 모델에서 1로 정규화합니다. `comboAxis: 'primary' | 'secondary'`는 견본의 자동 배정을 정하고 명시적인 계열 서식은 우선합니다. 같은 종류의 계열만 사용하더라도 콤보 편집 상태와 축 배정을 XLSX에서 유지합니다.

## 콤보 렌더링과 XLSX

- 누적 합계와 100% 분모를 **축과 계열 종류별**로 계산합니다. 보조 축의 큰 값이나 다른 종류의 계열이 주축 막대 비율을 바꾸지 않습니다.
- 양수·음수 막대 누적을 분리하고, 각 계열은 자기 축의 0 기준선·반전 설정을 사용합니다. 보조 축만 남아도 오류 없이 오른쪽 눈금과 제목을 표시합니다.
- 0, 음수, 빈 값, ±10¹² 값과 잘못된 동일 최소·최대 범위가 포함된 합성 차트에서 `NaN`·무한대 SVG 좌표가 생기지 않는지 확인했습니다. 모든 가능한 부동소수점 극단값을 검증한 것은 아닙니다.
- XLSX는 계열 순서·종류·축, 모든 계열이 보조 축인 경우, 축의 표시·주 단위·반전·숫자 서식을 왕복 검사합니다. 콤보 견본 선택은 WIXEL 확장 속성에도 보존합니다.

차트 UI의 새 선택 범위는 세로 막대·꺾은선·영역 조합입니다. 가로 막대와 세로 막대 혼합, 분산형과 범주 축 혼합, 선버스트 등 Excel의 모든 차트 조합을 지원한다고 주장하지 않습니다. 저장 후 다시 읽는 검사는 실제 Excel에서의 복구 메시지나 동일한 화면을 보장하지 않습니다.

## 피벗의 오류 값 표시 옵션

`showError` 플래그와 `errorCaption` 문구를 구분합니다. 문구만 남아 있거나 `showError="0"`인 파일에서 오류 숨김을 잘못 활성화하지 않습니다. 활성화하면서 문구가 비어 있으면 빈칸, `-`를 지정하면 해당 문구를 표시합니다. 비활성화하면 계산 오류를 그대로 표시합니다.

합성 XLSX에서 플래그 누락·0·1·false·true와 문구 누락·빈 문자열·문자열 조합을 검사했습니다. 브라우저 검사는 실제 파일 열기 입력으로 합성 XLSX를 읽고, 옵션 체크 상태·확인 후 셀 결과·정의·재저장 왕복을 확인합니다. 실제 사용자 파일의 기존 피벗 결과 차이까지 해결했다는 의미는 아닙니다.

## 시트 눈금선·셀 테두리

가는 선이 축소 화면에서 두껍게 보이는 문제를 DPR 2·배율 50%의 실제 PNG에서 재현했습니다. 기존 CSS 테두리는 검정 픽셀 두 줄로 보였고 수정한 경계는 한 줄로 표시됩니다. 이 비교는 해당 조건의 합성 시트에서 측정한 결과입니다.

- `grid-lines.js`가 공유 셀 경계를 한 번만 선택하고, 병합 셀의 긴 경계와 일부 구간의 굵은 선을 분리합니다. 같은 위치의 이중선 틈을 이웃 셀의 선이 메우지 않도록 처리합니다.
- 눈금선과 실선 테두리는 장치 픽셀 경계에 맞춘 SVG 사각형으로 그립니다. 실제 두께는 앱 배율과 DPR을 반영한 정수 픽셀로 정하며, 이중선은 두 선과 틈을 구분할 최소 두께를 유지합니다.
- `test/grid-lines.test.js`는 폭 계산, 중복 경계, 병합, 이중선, 숨김·서로 다른 축의 경계를 DOM 없이 검사합니다.
- `tools/grid-rendering.mjs`는 흰색·검정 테마 × DPR 1·1.25·2 × 앱 배율 50·75·100·125%의 **24개 조건**에서 브라우저 스크린샷을 만들고 PNG 픽셀을 직접 읽습니다. 계산된 CSS 폭만 비교하는 검사가 아닙니다.
- 가로·세로 thin/medium/thick의 실제 두께, 가장자리 번짐, 이중선의 두 줄과 간격, 첫 행·열, 병합 경계, 채우기 영역 네 면의 잔여 눈금선, 일반 눈금선의 1 장치 픽셀을 확인합니다. 숨김·틀 고정·분수 스크롤 뒤 클릭 좌표와 선택 표시, 필터 버튼 접근, F2 편집기 정렬도 검사합니다. 눈금선을 끄더라도 명시적인 셀 테두리는 남는지 확인합니다.

최종 소스 검사에서 **24개 조건·660개 검사**가 통과했고 페이지 오류·쓰기 요청은 0이었습니다. 작은 합성 문서의 `renderAll`은 3.6~7.4ms, 중앙값 5.1ms였습니다. 별도 경계 결합 측정은 긴 병합 경계 1개와 짧은 인접 경계 20,000개를 20,000개 구간으로 정리하는 데 22.34ms였으며, 이 수치를 대형 업무 파일의 전체 렌더링 성능으로 해석하지 않습니다. 실제 OS 모니터 전환·브라우저 자체 확대/축소·모든 화면 배율 조합까지 동일하게 확인한 것은 아닙니다.

## 검증 근거와 남은 범위

- [Microsoft의 차트 유형 안내](https://support.microsoft.com/en-us/excel/available-chart-types-in-office): 꺾은선 변형과 도넛의 여러 계열 표현을 참고했습니다.
- [Microsoft의 콤보 차트·보조 축 안내](https://www.microsoft.com/en-us/microsoft-365/blog/2013/01/25/need-to-combine-two-chart-types-create-a-combo-chart-and-add-a-second-axis/): 값 범위가 다른 계열의 축 배정을 참고했습니다.
- 이번 검사는 합성 문서와 기존 저장소 테스트를 사용했습니다. **실제 사용자 업무 XLSX/XLSB 및 Microsoft Excel 앱에서의 열기·표시·복구 여부는 검증하지 않았습니다.**
- 전체 단위 테스트 305/305, 일반·Cloudflare 빌드와 최종 번들 스모크 299명령 bad 0을 확인했습니다. 최종 번들 격자 검사도 24조건·660검사가 통과했습니다. 공개 주소 변경과 실제 배포 버전·공개 브라우저 확인 범위는 [12. 공개 배포와 운영 검증](12_공개배포와운영검증.md)에 기록했습니다.
