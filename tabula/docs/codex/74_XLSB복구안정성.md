# 74. XLSB 파일 전환·자동 저장·복구 안정성

## 범위와 판정 원칙

2026-10-04 사용자가 추가한 XLSB 3개를 원본 읽기 전용으로 검사한다. 실제 파일 이름·경로·셀 데이터·화면은 저장소나 공개 배포에 포함하지 않으며 D:의 비공개 검사 폴더에만 보관한다. 익명 ID X01–X03을 사용한다. 데스크톱 Chromium/WebKit 검사는 실제 iPad Safari의 OS 메모리 종료를 재현하거나 인증하는 검사가 아니다.

## 확인한 구조와 원인

- 압축 파일은 23.4–26.4MB이지만 압축 해제 총합은 496.4–574.7MB이다. 가장 큰 단일 시트는 305.7–363.1MB이다. 각 파일은 15시트이며 X01은 2,924,731개 수식 셀을 포함한다.
- 배포 기준 `493b7bf61ecadb10`에서 3개 모두 Chromium 대표 작업 75판정을 통과했다. 열기 27.2/36.6/37.0초, 검사 중 JS heap 관측은 약 1.0–1.34GB였다. 이 세션에서는 로딩 없는 본문 교체가 재현되지 않았다.
- D: 사본의 X01은 같은 기준 WebKit에서 가져오기 전용 8판정을 통과했다. 네트워크 드라이브 직접 입력은 WebKit 검사 프로세스의 파일 접근 오류였으며 제품 XLSB 파싱 실패와 구분한다.
- 큰 문서는 첫 자동 저장이 완료되기 전까지 이전 전역 복원 포인터를 유지했다. 페이지가 그 사이 종료되면 시작 화면은 이전 문서를 현재 문서처럼 복원했다. 같은 파일의 미저장 편집도 이전 완성본과 구분하지 않았다.
- 모든 큰 문서가 하나의 IndexedDB manifest와 정리 범위를 공유했다. 다른 탭의 저장이 현재 탭의 유일한 큰 문서 복원본을 대체할 수 있었다.
- IndexedDB 열기 실패의 rejected Promise와 닫힌 연결을 영구 재사용했다. 일시 오류 뒤 다음 자동 저장도 계속 실패하는 경로를 단위 fault injection에서 재현했다.
- 숨긴 피벗 필드 창의 DOM·드래그 리스너·문서 참조가 문서 전환 후에도 남았다. 시트 수가 적은 다음 문서를 열 때는 이전 시트 번호로 UI를 먼저 갱신해 열기가 중단되는 별도 오류도 재현했다.
- JSON 저장본을 복원할 때 동일 서식 객체를 셀마다 다시 생성했다. 수백만 수식 셀에서 중첩 글꼴·테두리까지 중복 보유할 수 있었다.

메모리 압박과 페이지 복원은 사용자 증상에 부합하는 위험 경로지만 실제 iPad 오류 당시의 OS 로그를 수집한 것은 아니다. 특정 기기의 종료 원인을 확정했다고 표현하지 않는다.

## 수정 구조

1. 성공한 문서 전환과 편집 직후 작은 문서 식별 기록을 동기 저장한다. 문서 ID, 페이지 세션, 열기 ID, 편집 버전, 저장 단계와 세대만 포함하며 본문을 복사하지 않는다. 완료된 저장본과 이 기록이 일치할 때만 자동 복원한다. 다른 문서·미저장 편집·읽기 실패는 복구 선택 화면으로 구분하고 이전 완성본을 삭제하지 않는다.
2. 큰 문서의 저장 위치와 정리 범위를 문서 ID별로 분리하고, 각 탭의 복원 포인터를 sessionStorage에 보관한다. 기존 단일 위치의 저장본도 읽는다. 오래된 탭의 완료 응답이 새로운 전역 복구 기록의 소유권을 가져가지 못한다.
3. 같은 문서를 두 탭에서 열었을 때 각 탭이 마지막으로 확인한 저장 세대를 비교한다. 다른 탭이 이미 저장했으면 그 완성본을 덮지 않고 현재 편집을 새 문서 ID의 별도 사본으로 저장한다. 자동 저장이 꺼진 명시적 저장도 한 번만 즉시 재시도하며 자동 저장 옵션은 유지한다. 새 사본 재시도에 실패하면 실제 시도한 문서의 정체성에 맞춰 지속적인 실패 상태와 안내를 표시한다.
4. 일시적으로 실패하거나 종료된 IndexedDB 연결은 재연결한다. 실제 트랜잭션을 시작하기 전 InvalidStateError일 때 한 번 재연결하며, 이미 시작된 쓰기·콜백·중단된 트랜잭션을 재실행하지 않는다.
5. 저장본을 읽을 때 완전히 같은 JSON 서식만 시트 내에서 공유한다. 캐시는 4,096종·키 문자 1Mi로 제한한다. 값·수식·서로 다른 자료형과 명시적 false 속성을 합치지 않는다. 개별 셀 서식 변경과 Undo/Redo는 이웃 셀에 영향을 주지 않는다.
6. 문서 교체 시 피벗 필드 창의 이벤트·DOM·문서 참조를 해제하고 새 문서의 유효한 시트 번호를 UI 갱신 전에 적용한다. 같은 문서 안에서 창만 숨기는 동작은 유지한다. 개체가 없는 새 시트나 아직 화면 범위가 정해지지 않은 시트로 바꿀 때도 이전 개체 렌더 캐시를 먼저 해제한다.
7. 다른 문서 열기를 시작하면 이전 문서의 진행 중 의존 그래프 준비를 취소하고, 문서 교체가 끝나면 이전 그래프를 해제한다. 화면 복귀 때 남은 자동 저장을 다시 예약하며 실제 미저장 상태를 표시한다. 새 문서 설치 직후에도 dirty 상태를 갱신한 다음 저장 대기 문구를 즉시 표시한다.

## 남은 제한

- 브라우저/OS가 저장 완료 전에 페이지를 강제 종료하면 미저장 변경 자체를 복원할 수 없다. 이번 수정은 다른 파일이나 오래된 내용을 최신 저장본처럼 조용히 표시하는 것을 차단한다.
- 초기 큰 저장은 일관된 완성본을 만들기 위해 편집 버전이 바뀌면 중단·재시도한다. 원자적 저장 보장을 완화하지 않았다. 첫 완성본 저장에는 충분한 시간이 필요하다.
- 문서별 큰 복구 사본은 다른 탭의 자료 보호를 위해 자동 삭제하지 않는다. 브라우저 저장 공간 한도·사용자의 사이트 데이터 삭제/비공개 모드·OS 종료 가능성은 남는다.
- 실제 iPad/iPhone/Android 메모리 제한과 하드웨어 입력은 별도 확인이 필요하다. 전체 Excel 동등성 판정과는 별개다.

### 출시 판정

롤백 방지와 저장 오류 처리 보완은 검증하여 배포한다. 실제 파일은 Chromium 개별 실행 3/3, WebKit 개별 실행 완료 1/3이며 나머지는 호스트 메모리 보호로 미검증이다. 연속 3파일 부하 검사는 통과하지 않았다. 물리 iPad 안정성, 무제한 대형 파일 처리 또는 Excel 전체 동등성을 보장하지 않는다.

## 추가로 필요한 대형 문서 설계

완성된 계산 캐시·실행 취소·피벗 값을 임의 삭제하는 방식은 사용하지 않았다. 현재 구조는 새 파일 파싱이 완료될 때까지 이전 작업 문서를 보존하므로 안전한 전환을 위해 두 모델이 잠시 공존한다. 모바일의 작은 메모리 예산을 만족하려면 시트별 지연 로딩, 저장 청크의 명시적인 수명 관리, 완료 저장본으로 돌아갈 수 있는 문서 전환 절차를 설계하고 실제 기기의 최대 메모리를 측정해야 한다. 이 작업은 아직 구현·검증되지 않았으며 현재 배포의 완료 범위로 포함하지 않는다.
