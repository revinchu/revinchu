# 대형 파일 저장·HTML·게시 안정성

## 문제와 설계

실제 XLSB는 압축 파일 크기보다 메모리상의 셀·수식·피벗 캐시가 훨씬 크다. 파일 크기만으로 저장 가능성을 판단하지 않는다. 전체 문서를 단일 JSON 문자열, 전체 워크시트 XML, 최종 ZIP Uint8Array로 중복 생성하던 경로를 분할 처리한다. 원본 파일을 덮어쓰지 않은 별도 저장본으로 검증한다.

- `wixel-file.js`: WIXEL v2 레코드 스트림을 gzip Blob으로 만든다. 셀·반복 스타일·피벗 스냅숏·typed array를 분할하며 레코드를 최대64KiB/2048개 단위로 묶어 수십만 개 압축 스트림 작업의 메모리 누적을 방지한다. 각 배치에서 현재 문서/버전을 검사한다. 읽기에서도 압축 입력과 UTF-8 해독 청크를 각각64KiB로 제한한다. 완전한 종료 레코드 없는 파일은 거부한다. 기존 JSON WIXEL 및 gzip JSON 링크는 계속 읽는다. 새 v2 파일은 업데이트된 앱이 필요하다.
- `xlsx.js`, `xlsx-compact-rows.js`, `zip.js`: 현재 시트의 숫자 행 인덱스만 계획하고 XML 청크를 ZIP 항목별로 압축한다. 표준 XLSX/XLSM/XLTX/XLTM 구분과 기존 byte API를 유지하며 앱은 Blob API를 사용한다. 수식·피벗 캐시·슬라이서·그림을 생략해 크기를 줄이지 않는다.
- `html-export.js`: HTML 내보내기를 인쇄 페이지 생성과 분리한다. 현재 시트 실제 사용 범위를 포함하고, 큰 표는 단일 파일 안에서 250행×64열씩 볼 수 있도록 페이지를 나눈다. 인쇄 2,000쪽 한도를 웹페이지 저장에 적용하지 않는다. HTML의 슬라이서는 저장 시점의 표시 사본이다.
- `publish.js`, `storage.js`: 기존 JSON API에 압축 파일을 일정 크기의 base64 청크로 담는다. 게시 중 문서/연결 변경을 검사하고, 서버 없이 만드는 URL은 압축 파일 크기를 먼저 검사한다. URL의 물리적 크기 제한을 데이터 누락으로 우회하지 않는다.
- `app.js`: 자동 저장에서 편집에 따른 스냅숏 취소를 실제 서버 오류와 구분하고 debounce 뒤 재시도한다. 업로드가 완료된 뒤 편집한 경우 수신한 서버 리비전을 유지하며, 이전 문서의 저장 작업은 새 문서의 저장 상태를 해제하지 않는다. 자동 게시는 문서·연결·게시 ID별로 한 번만 실행하고, 진행 중 추가 요청은 최신 스냅숏 한 번으로 합쳐 다음 리비전으로 전송한다. 저장 대상 선택 → 파일 생성 → 쓰기 완료 순서를 지킨다. 쓰기 실패 시 스트림을 abort하고 성공 안내를 하지 않는다. 파일 가져오기에서 피벗 재구성에 따른 수식 의존성 처리를 화면 설치 전에 마쳐, 뒤늦은 계산이 저장 버전을 변경하는 경합을 막는다.

## 실제 Excel 열기 실패의 원인

`styleForCode()`가 표시 형식 문자열을 `trim()`해 원본 `0.00_ `의 마지막 공백을 제거했다. `_` 다음 공백은 Excel 서식 언어의 피연산자이므로 `0.00_`는 다른 코드이며 Excel이 통합 문서 열기를 거부했다. XML·SDK 문법 검사와 위셀 재열기만으로는 검출되지 않았다. 최소 스타일 사본에서 공백 한 글자만 복구하면 Excel이 열리는 대조 검사로 원인을 확정했다.

원래 코드를 보존하도록 수정했으며, 이전 WIXEL 저장본에 이미 남은 끝자리 `_`·`*`·`\`의 누락 피연산자는 내보내기 사본에서만 공백으로 완성한다. 따옴표·조건식·이스케이프된 기호는 바꾸지 않는다. 별도로 XLSB 사용자 피벗 스타일 이름의 잘못된 바이트 오프셋과 표/피벗 대상 플래그, 슬라이서 fallback 그림의 중복 ID도 수정했다.

온라인 단일 문서/게시 한도는 실제 압축 게시본 약27.5MB가 저장되도록 32MiB로 조정했다. 보관함 현재 문서/이력은 각각100MiB, 게시물20개 한도는 유지한다. 합성27,536,555바이트와 정확한32MiB를 로컬 workerd에서 저장·읽어 SHA256 일치를 확인하고, 한도+1바이트 실패 시 기존 내용/버전 보존을 검사했다.

## 검증 범위

실제 업무 파일과 결과물은 저장소 밖 D:의 비공개 임시 디렉터리에만 둔다. 원본은 읽기만 하며 공개 게시 검사는 합성 문서를 사용한다. 테스트 도구 `tools/large-export-stress.mjs`는 localhost만 허용하고 `WIXEL_EXPORT_INPUT`을 명시해야 한다. `WIXEL_EXPORT_SHEET`를 지정하거나 피벗·슬라이서가 있는 첫 시트를 편집한다. 값과 수식은 좌표 기반 해시/합계/XOR, 피벗 스타일과 슬라이서 실제 표시색으로 저장 전후를 비교한다. 호스트 여유 메모리 1GiB 미만이면 검사를 중단한다.

실제 Excel은 별도 프로세스에서 읽기 전용으로 열며, 실행 중인 사용자 Excel과 원본 파일을 변경하지 않는다. ZIP CRC·XML 문법·관계 대상 검사와 실제 Excel 열기 검사를 별도로 수행한다. 자체 파서의 왕복 성공을 Excel 호환 완료로 간주하지 않는다.

## 실제 파일 검증 결과

약26.4MB XLSB의 피벗·슬라이서 스타일을 변경한 뒤 자동 저장을 켜 둔 Chromium에서 WIXEL → HTML → XLSX를 연속 저장했다. 수동 GC, 계산 그래프 제거, 데이터 생략 없이 완료했다. 환경별 속도·메모리 차이가 있으므로 아래 수치를 모든 기기의 성능으로 보장하지 않는다.

- 최초 테스트의 수식 해시는 실제 원문 대신 수식 여부만 반영한 결함이 있어 폐기했다. 개선한 원문 해시로 재검사했으며 XLSX의 텍스트 입력용 선행 작은따옴표 변환은 수식 변경과 별도로 대조한다.2개 시트의 비어 있지 않은318,990셀을 XLSX XML/SST까지 대조해479개 차이가 모두 접두 작은따옴표 정규화이며 값·문자열 자료형·수식의 예상 밖 차이는0개임을 확인했다.
- 최종 단위 검사1,658개, 백엔드 단위27개, 로컬 HTTP·복구 검사62개 통과. 문서 준비 중 편집·실패·취소·오래된 응답·리비전 경합은 Chromium/WebKit44개 검사로 확인했다. 추가 온라인 저장·자동게시 경합64개와 리본 명령387개(실행 오류0)도 통과했다. 최종 배포 번들의 WIXEL·XLSX·HTML 저장·취소·압축/기존 링크 열기·게시 중 문서 전환은 Chromium/WebKit6개 검사 모두 통과했다.

## WebKit 대형 검사 한계와 후속 계측

데스크톱 WebKit의 같은 XLSB 원본 열기는 셀 준비82%에서 호스트 가용 RAM이1GiB 아래로 내려가 도구가 중단했다. 대형 WIXEL 읽기 청크를 제한한 후 가용 RAM4,803,616,768바이트에서 시작한 재검사는34.197초에 문서 설치까지 성공했다. 그러나 저장 전에 검사 도구가 전체 셀을 집계하는 구간에서 보호 기준에 도달해 종료했다. 따라서 이는 **대형 WIXEL 열기 성공·대형 WebKit 저장 부하 미검증**으로 기록하며, 저장 실패나 실제 iPad 검증 성공으로 해석하지 않는다.

브라우저 오류0이며 가드를 낮추거나 사용자 프로세스를 종료하지 않았다. XLSB 복원은 이미 CellMap과 typed array 소유권을 넘겨받으므로 전체 셀 맵을 두 벌 복사하지 않는다. 약292만 수식 셀의 정규화 객체와 메타데이터 복제·GC 타이밍은 남은 메모리 피크 후보이며 원인은 확정하지 않았다. 후속 계측은 시트별 복원 시작/끝, 처리한 수식 수, 메타데이터 크기 및 실제 iPad의 메모리 종료 여부를 구분해야 한다.

## 남는 한계

무한한 문서 크기는 보장하지 않는다. 브라우저/기기의 메모리·디스크와 Excel 자체 행·열 한도는 유효하다. 큰 문서를 서버 없는 URL에 담을 수 없는 경우에는 온라인 게시 또는 파일 공유를 안내한다. 데스크톱 WebKit 검사를 실제 iPad/iPhone의 메모리·OS 동작 검사와 구분한다.
