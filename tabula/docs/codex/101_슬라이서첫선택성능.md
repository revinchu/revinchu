# 슬라이서 첫 선택 성능

2026-10-07. 기준은 4457259이며 브레인올로지 주간 리포트의 주차·캠페인 슬라이서 첫 선택 지연을 개선한다.

## 원인과 처리

실제 XLSB의 두 슬라이서는 각각 10개 피벗에 연결되어 있다. 첫 필터 적용에서 `applyPivotChanges → setSheetProp → invalidate → affected → sheetDeps`가 처음 통합 문서의 시트 참조 정보를 만들며, 같은 AST를 공유하는 수식도 셀마다 `formulaEntries`로 방문했다. 반복 선택은 이미 만들어진 참조 캐시를 이용하므로 빨랐다. 원본 큐브는 같은 저장 snapshot을 사용했고 피벗 결과 계산은 주차 첫 선택 전체 약 15ms였다.

CellMap은 수식 후보를 저장할 때 고유 AST와 참조 수를 유지한다. Workbook의 sheetDeps는 좌표별 수식을 펼치는 대신 고유 AST만 방문한다. 해석 실패 AST는 보수적인 전체 의존으로 처리한다. 수식 삭제·덮어쓰기·정규화·희소 이동·되돌리기에서 요약도 갱신한다. 피벗 정의 변경의 재계산과 GETPIVOTDATA 의존 계약은 유지한다.

슬라이서 필터가 transaction으로 변경되면 onBookChange가 예약한 한 번의 화면 갱신으로 격자·개체·선택을 완성한다. 그 전에 중복 layout와 개체 렌더를 실행하지 않는다. 변경 없는 선택, 보호 거절, 연결 오류 및 피벗 겹침 거절에는 즉시 표시 경로를 유지한다.

기존 피벗 역할 정보를 만들지 않는 빠른 경로는 사용하지 않는다. 옛 병합 해제와 보고서 필터 사이 사용자 셀 보존에 필요하기 때문이다.

## 검증 범위

합성 브라우저 도구 `tools/slicer-selection-performance-ui.mjs`는 큰 열 블록, 연결 피벗 1/4개, 주차·캠페인 교차 조건, 다중/필터 지우기, 빠른 연속 입력, 실행 취소·다시 실행, 중복 연결 및 피벗 충돌의 원자성을 검사한다. 단계별 이벤트 시간과 렌더 수를 기록하며 기계별 고정 시간 한도를 통과 조건으로 사용하지 않는다.

실제 업무 파일은 로컬 읽기 전용으로 사용한다. D:의 Git 제외 폴더 .local/slicer-selection-performance에 원시 프로파일·스크린샷·검사 로그를 보관하고 공개 검증에는 합성 문서만 사용한다. 네이티브 Excel의 처리 시간을 직접 비교한 결과는 아니다.

후보별 이전 AST를 보관하는 작은 레코드 때문에 메모리 대가가 있다. 백만 수식 후보의 합성 GC 후 측정은 약 38.16MiB 추가였다. 실제 파일 후보 수에 비례한 약 78MiB는 추정치이며 실제 앱 전체 heap 측정과 구분한다. 통합 문서 전체 복사나 새 좌표 인덱스는 추가하지 않는다.

## 실제 첫 선택 시간

다른 검사를 모두 끝내고 유휴 상태에서 수정 후 주차·캠페인을 각각 새 브라우저 문서로 가져와 같은 항목을 4번씩 선택했다. 기준과 같은 로컬 컴퓨터의 개별 관측이며 반복 횟수 8회이고 Excel 네이티브와의 속도 비교는 아니다.

| 첫 선택 | 기준 handler | 수정 handler | 기준 입력→2RAF 화면 확인 | 수정 입력→2RAF 화면 확인 |
|---|---:|---:|---:|---:|
| 주차 | 230.8ms | 35.3ms | 340ms | 124ms |
| 캠페인 | 193ms | 26ms | 282ms | 123ms |

처음 시트 의존성을 만들 때 8개 시트의 고유 AST 36개만 방문했고 0.5~0.6ms가 걸렸다. 후속 세 클릭은 AST 방문과 sheetDeps 생성 모두 0회였다. 변경마다 layout 1회였으며 첫/후속 8클릭 전체에서 피벗 정의·영역·단추·필터·출력 해시와 슬라이서 선택 상태가 기준과 완전히 같았다. 슬라이서의 저장 좌표는 기준과 같고 실제 DOM 위치는 수정 후 첫 상태부터 모든 클릭에 동일했다. 원본 SHA-256·크기·수정 시간 불변, 브라우저 오류·외부 쓰기 0건이다.
