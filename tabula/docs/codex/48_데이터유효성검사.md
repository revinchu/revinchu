# 데이터 유효성 검사

2026-10-03. 데이터 유효성 검사 편집기, 후보 입력 판정, 목록 참조와 XLSX 보존을 보강했다. 이번 작업은 아래 범위의 구현과 합성 검증이며, Excel의 모든 입력 경로·함수·플랫폼과 완전히 같음을 보장하지 않는다.

## 편집과 적용

설정·설명 메시지·오류 메시지·IME 모드의 네 탭을 제공한다. 모든 값, 정수, 소수점, 목록, 날짜, 시간, 텍스트 길이, 사용자 지정 규칙과 8개 비교 연산자를 사용한다. 설명 메시지와 정지·경고·정보 오류 스타일을 편집하며, 날짜 체계는 통합 문서의 1900/1904 설정을 따른다.

- 편집은 초안에만 반영한다. 모두 지우기도 초안을 초기화하며, 확인해야 적용된다. 취소는 원래 규칙을 유지한다.
- 같은 설정 전체 적용은 선택한 규칙과 같은 설정의 시트 내 규칙을 함께 바꾼다. 서로 다른 규칙이 섞인 선택에서는 혼합 상태를 안내하고 이 기능을 비활성화한다. 혼합 선택은 별도 Excel 확인창 대신 편집기 안의 경고로 안내한다.
- 확인할 때 통합 문서·시트·선택·기존 규칙과 읽기 전용·보호 상태를 다시 확인한다. 적용과 삭제는 한 번의 실행 취소로 되돌린다.
- 범위 선택 단추로 조건이나 목록 원본을 지정한다. 탭 키보드 탐색과 좁은 화면의 스크롤 배치를 제공한다.
- IME 모드 11개는 파일 속성으로 보존한다. 브라우저에서 Windows 한/영 전환, 전자·반자나 일본어 변환 모드를 강제로 바꾸지는 않는다.

## 판정과 원본 보호

`src/validation.js`의 `checkValidation(wb, si, rule, r, c, text)`는 후보 입력을 판정한다. `=`로 시작하는 입력도 계산한 결과를 검사한다. 숫자 규칙의 계산 오류나 잘못된 조건을 성공으로 처리하지 않는다. 사용자 지정 규칙은 규칙 자체의 결과로 판단하므로, 후보가 오류 값이어도 후보와 무관한 조건이 참이면 허용할 수 있다.

`src/validation-eval.js`의 `validationEvaluation`은 후보 입력을 별도 계산 문맥과 메모에 놓는다. 원본 셀에 임시 값을 쓰거나 통합 문서 전체를 무효화하지 않는다. 참조 수식·이름을 이 문맥에서 평가하며, 파일에서 읽은 계산값, 원본 캐시, 분산 배열 기록, 변경 버전과 Undo 이력을 변경하지 않는 회귀를 포함한다. 계산하지 못한 수식의 파일 저장값을 정상 판정값으로 대신 사용하지 않는다.

공백 무시는 필수 입력 설정과 다르다. 해제했을 때도 숫자 0, 길이 0 또는 사용자 지정 조건으로 빈칸을 허용할 수 있다. 텍스트 길이는 이번에 대조한 Excel과 같이 UTF-16 길이를 사용한다. 빈 참조 조건, 빈칸이 포함된 이름 목록, 참조가 나중에 오류로 바뀌는 경우도 합성 Excel 결과와 대조했다.

## 목록·상대 참조 API

- `validationList(wb, si, rule, r?, c?)`는 `items`, `itemValues`, `values`, `literal`, `limited`, `error`를 반환한다. `items`는 표시 문자열, `itemValues`는 같은 순서의 원시 값이다. 숫자·날짜를 표시 서식으로 반올림한 문자열과 구분한다. 같은 표시 문자열은 첫 원시 값으로 묶으며, 판정용 `values`에는 원래 값들을 유지한다. 직접 입력 목록은 `literal: true`다.
- 기존 `listItems(...)`는 표시 문자열 배열을 반환하는 호환 API다. 이름, 다른 시트 참조, `INDIRECT`·`OFFSET`과 1차원 수식 결과를 처리한다. 원본의 숫자 서식과 날짜 체계로 목록 문구를 표시한다.
- `relocateValidation(rule, range)`는 규칙의 적용 기준점을 옮기고 상대 참조를 함께 이동한다. `subtractRange`도 남는 조각마다 이를 적용하여 범위 일부를 지운 뒤 조건이 바뀌는 문제를 막는다.
- `validationSignature(rule)`는 좌표를 제외한 설정과 상대 참조 오프셋을 비교한다. 오류·설명 메시지, 표시 여부와 IME 모드도 포함한다. 수식을 A1으로 강제로 옮겨 서로 다른 참조가 같은 `#REF!`가 되는 방식은 사용하지 않는다.
- `validateValidationRule(wb, si, rule)`는 설정이 유효하면 `null`, 아니면 한국어 오류를 반환한다. 빈 조건, 뒤집힌 최소·최대값, 잘못된 목록·수식, 시간 범위 등을 확인한다.
- `invalidCells(wb, si, limit=2000)`는 일반 셀과 가져온 열 블록의 실제 값들을 검사한다. 겹치는 규칙은 마지막 적용 규칙을 따르며, 같은 목록 원본을 반복 읽는 작업은 한 검사 안에서 재사용한다.

## XLSX 보존

표준 `dataValidation`의 유형·연산자, 공백 무시, 목록 단추, 입력·오류 메시지 및 표시 여부, 오류 스타일, `imeMode`, `formula1/2`를 읽고 쓴다. 유형이 모든 값인 메시지·IME 전용 규칙도 유지한다. 직접 입력 목록과 이름·함수 목록을 구분하여 저장하며, 여러 `sqref` 범위는 첫 범위 기준 수식을 각 범위로 이동하여 모델에 넣는다.

이번 신규 입출력 보강은 XLSX에 한정한다. 기존 XLS/XLSB 경로의 데이터 유효성 검사 전체를 같은 수준으로 검증한 것은 아니다.

## 확인한 검증과 제한

- 전체 Node 단위 검사 **986/986** 통과, 실패 0. 신규 `test/validation-parity.test.js`는 **21/21**이다. 수식 후보, 원본·계산 캐시 불변, 상대 참조, 이름·목록, 블록 데이터, 공백, 원시 값 정밀도, IME와 XLSX 왕복을 포함한다. 최종 로그는 `.local/validation-all-unit-final.log`다.
- 별도 숨긴 Excel 16.0 build 14334 인스턴스로 합성 규칙을 검사했다. 후보 103개, 나중 참조 오류 30개, 공백 10개를 합쳐 **143개 중 142개**가 Excel COM `Validation.Value`와 일치했다.
- 남은 한 건은 목록 `Alpha`에 `alpha`를 넣은 경우다. COM은 거절하고 WIXEL은 기존 대소문자 무시 동작으로 허용한다. Excel의 실제 직접 입력·자동완성 UI를 대조하지 않았으므로 입력 동등성이 확인되었다고 보지 않는다.
- WIXEL이 저장한 합성 파일을 Excel에서 정상 열고 재저장했다. **40개 규칙의 8개 속성 차이 0**, OpenXML SDK의 **3개 전체 패키지 오류 0**이었다. 오류 수식 3개가 Excel의 규칙 생성 단계에서 거절되는 것도 확인했다.
- 브라우저 유효성 검사 회귀는 소스와 최종 번들에서 각각 **36/36(272 assertions)** 통과했다. 최종 CSS의 네 탭·모바일 배치는 **6/6(51 assertions)**, 명령 스모크는 **382개 `bad 0`**, 기본 UI는 **12/12**, 기존 WIXEL UI는 **10/10**이었다.
- 실제 업무 파일 2개도 변경 전후를 읽기 전용으로 비교했다. 정산 파일 수식 8,545개와 여행 파일 수식 698개의 계산 불일치·저장 후 재열기 문제는 각각 **0→0**이었고 원본 SHA256도 동일했다. 두 파일에는 피벗·유효성 검사 규칙이 없으므로 해당 기능의 검증 근거로 포함하지 않는다.
- 목록 원본은 최대 100,000개이며 2차원 목록과 한도 초과는 오류로 알린다. 전체 행·열 참조는 사용 범위로 제한한다. 격리 수식 계산은 셀 읽기·범위 1,000,000개와 재귀 깊이 100의 상한을 둔다. 잘못된 데이터 표시는 기본 최대 2,000개이며 비어 있는 전체 시트를 전수 조사하지 않는다.
- 지원하지 않는 함수, 후보로 새로 생기는 분산 영역의 빈 셀을 직접 참조하는 고급 조건, 피벗 재계산까지 포함한 판정은 이번 검증 범위가 아니다. 복사·붙여넣기 등 모든 입력 경로에 Excel과 동일한 경고가 나타난다고 주장하지 않는다.

네이티브 검증은 합성 자료만 사용했다. 사용자 문서나 기존 Excel 인스턴스를 변경하지 않았으며, 세부 자료는 저장소 밖 `D:/Codex/Temp/wixel-validation-oracle/`에 보관한다.
