## 판정 원칙

2026-10-03 시작, 2026-10-04 계속 검수 중이다. 사용자가 지정한 실제 업무 파일 20개(XLSX 17개, XLSB 3개)를 대상으로 한다. 원본은 읽기 전용으로 검사하고 크기와 수정 시각을 전후 확인한다. 실제 파일·셀 내용·원본 경로·스크린샷·Excel PDF는 커밋하거나 공개 서버에 올리지 않는다. 결과 원문은 사용자의 D: 임시 검사 폴더에 있으며 이 문서에는 익명 파일 ID와 집계만 기록한다.

단순히 열렸다는 사실을 Excel과 동일하다는 판정으로 사용하지 않는다. 파일 열기, 구조·옵션, 화면, 계산·상호작용, 편집·복원, 성능을 분리한다. 건너뜀·시간 초과·도구 오류는 통과가 아니다. 실제 iPhone/iPad 메모리 제한·운영체제 입력은 Windows의 headless WebKit 검사로 인증할 수 없다.

## 검사 설계

1. 20개 원본의 존재·크기·형식을 검사한다. ZIP 중앙 디렉터리에서 압축 해제 후 크기와 큰 항목을 파악한다.
2. 별도의 Excel 16 인스턴스로 읽기 전용 열기, 매크로·이벤트·외부 링크 갱신 차단, 시트·보기·셀/행/열 서식·표·피벗·슬라이서·도형 기준값을 얻는다. 기존 사용자 Excel 인스턴스는 건드리지 않는다.
3. 격리한 로컬 Chromium/WebKit에서 실제 파일 입력으로 연다. 모든 표시 시트의 렌더·스크롤, 편집·실행 취소, 같은 문서 유지, 오류 및 경고를 기록한다. API 쓰기·외부 요청은 차단한다.
4. 연결된 슬라이서 단일/Ctrl 다중 선택·해제·Undo와 피벗 필터 검색·현재 선택 추가를 실제 UI로 확인한다. 모든 개체의 전 조합 검사와 대표 상호작용 검사를 구별한다.
5. 문서 전환·두 탭·자동 저장과 재열기를 검사한다. 피벗의 저장 캐시와 원본 셀 값이 다를 때 어느 값이 유지되는지 별도로 확인한다.
6. 피크 메모리를 고려하여 큰 파일 검사는 순차 실행한다. Excel과 브라우저를 동시에 실행한 시간은 독립 성능 측정으로 사용하지 않는다.

- Excel COM의 `SplitRow`, `AutoFilter.Range`, `UsedRange.FormatConditions`가 원본 저장 XML/BIN과 다른 사례를 따로 분류했다. 확인한 원본 필터/고정창/규칙 값이 위셀과 일치하면 가져오기 손실로 집계하지 않는다. 미확인 차이는 검토 상태로 유지한다.
- 수식의 `[@열]`과 `표[[#This Row],[열]]`, 표시 형식 이스케이프, Excel COM의 수평 회전 상수 등 표현 차이와 의미 차이를 분리한다. 표본 수식 결과가 같아도 전체 계산 엔진이 같다는 증거는 아니다.
- F15의 `#UNKNOWN!`/`#VALUE!` 차이는 셀 안 그림/리치값 메타데이터 누락으로 확인됐다. 원본은 `BrtValueMeta`가 그림 메타데이터를 가리키고 오류 셀에는 대체 표시용 `#VALUE!`가 저장되어 있다. 값 메타데이터를 삭제해 그림 연결이 사라졌으므로 단순 오류 바이트 치환으로 해결하지 않는다. 기존 richData 경로 연결 수정과 합성 회귀가 완료됐으며 최종 실제 파일에서 181좌표의 그림 존재, 고유 source 99개, 인접 792좌표에 그림이 번지지 않음을 확인했다. 이는 셀별 그림 바이트/전체 픽셀 동일성을 인증한 검사는 아니다. 원본에는 고유 그림 99개가 181셀에 배치되어 있으므로 고유 이미지 수와 셀 배치 수를 혼동하지 않는다. native가 미지원 리치값을 #UNKNOWN!으로 반환하고 위셀에 실제 셀 그림이 있는 경우 숫자 계산 실패와 별도로 기록하며, 그림 배치와 인접 792좌표는 전용 검사로 대조했다. 별도로 발견한 GETTING_DATA 오류 바이트 매핑 문제와도 구분한다.
- 이전 F11/F12/F13의 `performance.memory` 10.6MB 고정값은 브라우저 계측 정밀도 제한이다. 실제 적은 메모리 사용량으로 인용하지 않는다. 최신 실행은 정밀 메모리 계측과 CDP 표본을 병행하고 JS heap/프로세스·OS 여유 메모리를 구분한다. F03의 마지막 heap 3.85GB도 전체 프로세스 피크 또는 모바일 가용 메모리를 뜻하지 않는다.
- UI 타임아웃은 데이터 기능 실패와 성능 실패를 구분해 재검사한다. F15 후속 검사는 최대 90초까지 관찰했다. 단일/Ctrl 선택·해제·Undo 묶음은 21.632초로 완료되어 기능 성공/성능 실패로 남긴다. 같은 실행의 우클릭은 0.939초, 피벗 필터 검색 묶음은 0.212초였다. 각 묶음 시간이며 모든 지연이 단일 클릭에서 발생했다고 단정하지 않는다.
- 현재 표본과 개체 수 비교는 조건부 서식 모든 규칙, 차트 모든 옵션, VBA/Power Query/OLAP 계산, 전체 셀·수식·인쇄 픽셀 및 실제 모바일 OS 입력까지 포괄하지 않는다.

### 청크 수정 후 F20 저장 왕복

701ee4 컴파일본에서 실제 앱 저장 명령으로 60,830,024바이트 XLSX 사본을 생성했다. 새 context에서 이 사본을 열어 8시트/피벗30개/슬라이서40개/차트4개/표1개/개체52개, 64개 값·수식·직접 서식 표본이 일치했고 25판정/46.3초를 기록했다. 저장 전후 보기·숨김·크기·인쇄·개체 등 모델 메타데이터 208항목도 같았다.

이 후속 검사에서 실행 가능한 슬라이서 클릭 대상이 없어 해당 항목은 **skipped**이며 통과로 바꾸지 않았다. 최종 원본 Chromium/WebKit 검사도 동일한 skipped 상태였으므로 저장 후에 새로 발생한 슬라이서 회귀라는 근거는 없다. 피벗 필터 검색 검사는 실행했다. 이전 다른 실행에서 확인한 Ctrl 선택 기능과 최종 이 실행의 skip을 혼합하지 않는다.

필터 active 옵션 차이 1건은 원본과 사본의 표 autoFilter 하위 조건이 revision uid를 제외하면 완전히 동일함을 확인했다. 필터 범위와 두 열의 조건 값이 보존됐으므로 조건 소실로 판정하지 않는다. 후속으로 정상 열린 기능 분리 사본에서 Worksheet.FilterMode=false와 ListObject.AutoFilter.FilterMode=true/활성열2개를 동시에 확인했다. 감사 도구가 시트 상태와 표 조건을 합쳐 비교한 오류였으므로 두 계층을 분리했고 작은 회귀가 통과했다. 이전 원문 판정은 덮어쓰지 않고 도구 오판으로 재분류한다.

그러나 실제 Excel 16에서는 이 다운로드 사본의 normal 열기가 약5.1초 후 **1004 오류로 실패**했다. 사본만 대상으로 한 읽기 전용 복구 진단도 약13.9초 후 실패했고 복구 XML 로그가 생성되지 않았다. 두 실행에서 사본 크기/수정시각은 같고 별도 Excel은 종료했다. 업무 원본에는 복구나 저장을 하지 않았다. ZIP157항목/총해제588,453,481바이트의 CRC와 XML154개 문법은 별도 검사에서 정상이었으므로, 표준 컨테이너가 읽힌다는 것만으로 Excel 스키마·관계·캐시 의미 조건까지 정상이라고 판정하지 않는다. **다운로드 생성 문제의 해소와 Excel 호환 P0의 미해결을 구분한다.**

### Excel 거부 원인의 분리 진단

같은 청크 writer로 만든 작은 4만행 합성 문서는 실제 Excel normal 열기/RepairMode=false를 통과했고 한글·emoji, 첫/마지막 행 6값과 2수식이 일치했다. F20 다운로드 사본의 157개 항목을 Python 표준 ZIP으로 본문 CRC/해제 크기 그대로 재포장한 문서는 여전히 normal 열기1004로 거부됐다. 새 ZIP 출력 방식 전체가 잘못됐다는 설명은 이 대조 결과와 맞지 않는다.

- 큰 내보내기: 행 iterator와 피벗 cache accessor는 중간 자료구조의 복제만 제한한다. 최종 XML 문자열/압축 버퍼의 최대 크기와 모바일 다운로드·재열기 성공은 별도 검증 항목이다. 실제 F20 저장에서 문자열 크기 오류가 재현되어 이 제한은 잠재 위험이 아닌 확인된 P0로 승격했다. 후속 수정은 worksheet/sharedStrings/cacheRecords를 제한 크기 문자열 조각으로 만들고 ZIP에서 UTF-8·CRC·압축을 순차 처리한다. 독립 zlib/CRC/header 기준의 합성 7개 검사는 통과했지만 실제 F20 저장 및 Excel 재열기 성공 전에는 P0 해결 완료로 판정하지 않는다. 최종 Uint8Array 출력과 ZIP32 한계도 남는다.

Open XML SDK2.20.0의 Office2021 루트 스키마 검사에서 피벗/캐시33파트 오류0이었다. 전체 패키지 의미 검사에서 대체 도형 ID0 중복7건이 나왔으나, 원본의 그림 파트를 그대로 사용한 대조에서도 같은7건이었다. 이 경고는 원본과 동일한 SDK 진단이며 위셀에서 새로 만든 제품 결함으로 집계하지 않는다. **SDK 스키마 통과는 실제 Excel 정상 열기 통과를 대신하지 않는다.** SDK 바이너리는 D: 캐시에만 두고 저장소에 넣지 않는다. 검증 API와 패키지 버전은 [공식 검증 안내](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-validate-a-word-processing-document)와 [Open XML SDK 2.20.0](https://www.nuget.org/packages/DocumentFormat.OpenXml/2.20.0)을 기준으로 하며, 위 건수는 실제 실행 결과다.
