# 아이폰 수식 오타 안내와 명시적 수정

아이폰의 가져오기 화면에 표시된 372개는 확인되지 않은 함수 이름을 포함한 수식 셀 수다. 익명 검체를 조사해 `SUMIFS` 뒤에 한글 `ㅋ`가 붙은 `SUMIFSㅋ`가 원본 수식 372개와 표 계산 열 템플릿 1개에 있음을 확인했다. 함수 이름 판별은 공통 수식 파서와 함수 목록을 사용한다. 이번에 확인한 원인은 원본에 저장된 함수 이름이며, 물리 아이폰 Safari의 별도 계산 결함으로 판정하지 않는다.

원본의 372개 수식은 모두 `IFERROR(IFS(...),0)` 형태다. 조건상 잘못된 이름의 분기를 선택하는 31개는 원본 저장값도 모두 0이었다. 나머지 341개는 정상 `SUMIFS` 분기를 선택하며, 그중 61개에 0이 아닌 저장값이 있었다. 함수 이름의 정적 검사와 실제 조건 분기·오류 처리를 구별해야 한다. 이 때문에 안내를 없애는 것만으로 업무 수식의 오타가 수정되지는 않는다.

## Excel 기준 확인

Microsoft의 [IFERROR 설명](https://support.microsoft.com/en-us/excel/functions/iferror-function)은 `#NAME?`를 포함한 오류에 지정된 대체값을 반환하는 동작을 설명한다. [IFS 설명](https://support.microsoft.com/en-us/excel/functions/ifs-function)은 첫 번째 TRUE 조건의 결과를 반환한다고 설명한다. 함수 이름의 오타는 [이름 오류 설명](https://support.microsoft.com/en-us/excel/how-to-correct-a-name-error)에서 확인할 수 있다. 이 문서만으로 내부 평가 순서 전체를 단정하지 않고 아래 합성 결과를 함께 사용했다.

별도 합성 Excel 인스턴스에서 20개 수식을 6개 입력·수정 단계로 비교했다. Excel 16.0 빌드 14334와 WIXEL의 120개 결과가 모두 같았으며 차이는 0이었다. 선택되지 않은 잘못된 함수의 분기, 선택된 이름 오류, `IFERROR`의 0 대체, 정상 분기와 입력 변경을 포함한다. 사용자 원본을 이 Excel 검증에 열거나 수정하지 않았다. 소유한 합성 인스턴스만 종료했고 기존 사용자 인스턴스는 유지했다. 이번 수정으로 계산 엔진의 `IFS` 출력 의미나 전역 함수 목록을 바꾸지 않았다.

## 안내와 명시적 수정

가져오기 안내는 확인할 함수 이름과 해당 수식 셀 수를 보여 준다. 함수 이름 목록은 처음 8개로 제한하고 나머지는 `등`으로 표시한다. 원본에 이미 저장된 `#NAME?` 오류, 수식 문자열 안의 함수처럼 보이는 글자와 정의된 함수는 기존 판별 규칙으로 구별한다. `IFERROR`와 `IF`·`IFS`의 조건 처리를 계속 계산한다는 설명을 함께 제공한다.

사용자는 가져오기 창의 **함수 이름 확인...**, **계산 상태 확인** 창의 **함수 이름 수정...**, 수식 메뉴의 **함수 이름 수정...**에서 후보를 검토한다. `formulaNameRepair` 명령이 같은 창으로 연결된다. 창은 `SUMIFSㅋ → SUMIFS`와 같은 변경, 셀 수식·표 템플릿의 개수, 처음 20개 대상 위치를 보여 준다. **수정 적용**을 눌렀을 때만 현재 문서에 적용하며 **취소**와 일반 열기·저장은 원문을 유지한다. 검토 계획은 이 창을 열 때 만들고 일반 가져오기 중에는 계산하지 않는다.

`formula-name-repair.js`의 적용 범위는 다음과 같다.

- 알려진 함수 이름 바로 뒤에 한글 한 글자가 붙은 경우만 후보로 제안한다. 다른 철자나 여러 글자의 오류는 직접 확인한다.
- 수식 토큰의 해당 함수 호출만 바꾼다. 문자열·시트 이름·구조적 참조의 열 이름은 보존한다.
- 통합 문서·시트 범위의 정의된 이름과 `LET`·`LAMBDA` 지역 함수는 유지한다. 같은 철자가 바깥에서는 오타이고 안에서는 지역 함수일 때도 호출 위치와 범위를 각각 판정한다. 구문을 읽지 못한 후보는 추정하지 않는다.
- 계획은 원본 통합 문서와 버전에 묶이고 변경 전·후 원문을 보관한다. 적용 전에 모든 대상의 현재 원문·이름·시트·표를 검사한다. 문서가 바뀌었거나 보호·외부 시트가 포함되면 전체 계획을 거절한다. 읽기 전용·최종본 문서도 적용하지 않는다.
- 셀 수식과 표 템플릿의 변경은 하나의 트랜잭션과 실행 취소 단계로 기록한다. 셀의 서식·메모·링크·수식 입력 형식은 유지하고, 수정된 수식의 이전 계산 캐시는 버린다. 의존 수식은 기존 의존 그래프로 갱신하며 공유 AST를 변경하지 않는다.
- 표 템플릿만 바꾸는 속성 기록은 계산 중립으로 처리한다. 같은 시트의 무관한 미지원 저장값을 버리지 않는다. 기존 수동 계산 모드를 유지하므로 계산 대기는 F9로 반영한다.

명시적 수정 검토에서는 셀 수식 372개와 템플릿 1개가 대상이었다. 원래 잘못된 분기를 선택한 31개 중 6개와 이를 참조한 12개의 저장 결과가 바뀌어 계산 캐시 변경은 총 18개였다. 이는 수식 오타 수정으로 생긴 결과 변경이며, 원본의 값을 그대로 보존하는 기본 열기 검증과 구분한다. 변경 전·후 업무 값은 공개 문서에 포함하지 않는다.

## 표 계산 열 템플릿 보존

표의 `<calculatedColumnFormula>`를 `table.calculatedColumnFormulas = { [절대열]: '=수식' }`에 보관한다. 파일 수식은 가져오기 변환을 거쳐 앱 수식으로 저장하고 내보낼 때 표 이름을 반영한 파일 수식으로 변환한다. 가져올 때 템플릿으로 현재 데이터 행을 채우지 않는다.

현재 데이터 행이 모두 같은 구조화 수식이면 그 수식을 내보내는 템플릿으로 사용한다. 상수·빈 셀·다른 수식의 예외 행이 있으면 보관한 템플릿을 유지한다. 명시적 함수 이름 수정은 실제 셀과 보관한 템플릿을 함께 바꾸므로 저장한 뒤 이전 오타가 템플릿에서 다시 나타나지 않는다. 계산 열의 예외는 [Microsoft 오류 검사 설명](https://support.microsoft.com/en-us/excel/detect-formula-errors-in-excel), 형식은 [Open XML CalculatedColumnFormula](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.spreadsheet.calculatedcolumnformula?view=openxml-3.0.1)를 참고한다.

행·열 삽입/삭제, 표 전체를 이동하는 셀 삽입/삭제와 시트 이름 변경은 템플릿 참조도 기존 수식 변환 경로로 갱신한다. 열 이동에서는 절대 열 키를 조정하고 삭제된 열의 템플릿만 제거한다. 이 metadata와 참조 변경도 Undo/Redo에 포함한다.
