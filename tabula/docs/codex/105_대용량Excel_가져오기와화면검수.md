# 대용량 Excel 가져오기와 화면 검수

102MB Excel 파일의 iPad Safari 종료 신고와 추가 업무 파일 11개를 대상으로 가져오기 메모리, 편집 이력, XLSX 저장·재열기, 셀 및 개체 서식을 조사했다. 원본은 읽기 전용으로 다루며 SHA256·크기·수정 시각을 확인한다. 비공개 파일·저장 사본·화면·상세 검증 로그는 D:의 무시된 .local/large-xlsx-ipad 아래에만 보관한다. 공개 자료에는 익명 검체 번호와 합성 회귀만 포함한다.

## 구현

- File/Blob의 ZIP 목록과 필요한 압축 항목만 읽는다. 큰 워크시트·공유 문자열·피벗 레코드는 전체 압축 해제 버퍼를 만들지 않고 32KiB 사전과 제한된 출력 청크로 해제한다. CRC·실제 크기·XML 끝을 검사하고 항목 사용 뒤 원문을 해제한다. 기존 바이트 입력과 동기 읽기는 유지한다.
- 시트 XML은 현재 행과 전후 메타데이터만 유지한다. UTF-8·네임스페이스·CDATA·주석·태그 경계·비정렬 좌표를 검증한다. 넓은 행에서도 셀 처리량을 기준으로 UI에 제어를 돌려준다.
- 같은 서식의 빈 셀을 가로 구간과 직사각형으로 모으고, 같은 열 패턴은 불변 저장 자료를 공유한다. 셀 위치와 논리 개수는 유지하며 수정 때 해당 저장 자료만 분리한다. 실행 취소의 내부 시트 사본도 같은 표현을 사용하여 수백만 빈 셀을 펼치지 않는다.
- 피벗 캐시 열의 반복되는 끝부분은 값과 시작 위치로 보관한다. 처음부터 백만 행 배열을 할당하지 않고 작은 접두 배열에서 시작한다. 중간 값이 달라지면 필요한 구간을 복구한다. 논리 행 수·항목 순서·형식과 JSON/WIXEL/IndexedDB/XLSX 읽기·쓰기를 유지한다.
- 수식 후보 색인에서 셀 객체를 중복 보관하는 포장을 제거한다. 좌표와 공유 AST의 관계, live iteration, 구조 변경 후 후보 갱신은 유지한다. 기존 수식 셀 비교에서 stale 캐시 값과 배열 캐시 신뢰 상태를 무시하던 결함도 고쳐 값 변경·실행 취소를 보존한다. 수식 의존 그래프의 목록 수집도 2만 수식마다 나누고 열 정렬 뒤 취소·시간 예산 검사 지점을 둔다. 계산 등록 순서·공유 AST·묶음은 유지한다. 정렬 자체와 후보 내부 스캔의 강제 시간 상한은 보장하지 않는다.
- 가져온 General 서식의 소수 자릿수를 고정 0으로 해석하던 문제를 수정한다. 명시적 General은 열·행의 숫자 서식을 가리는 원래 의미도 유지한다. 셀 스타일 customBuiltin의 부재/false/true와 셀 서식 대화상자의 아래쪽 정렬도 구별한다.
- 슬라이서 startItem을 읽고 저장하며 표시 순서·열 수·버튼 높이에 따라 첫 스크롤을 맞춘다. 가상 목록, 같은 문서의 사용자 스크롤 0, 새 문서의 시작 위치를 구별한다.
- 피벗 조건부 서식의 selection 범위와 worksheet pivot 표식을 저장한다. 실제 검체의 지원되는 조건부 서식 2,499개는 범위·순서·색·음수 색·임계값이 보존됐다. 기존 모델의 같은 우선순위 다중 피벗 연결과 일부 상세 항목 참조는 별도 한계다.

- 외부 또는 처음부터 없는 피벗 원본은 가져온 원본 연결과 캐시 ID를 함께 검증한 뒤 저장 캐시를 사용한다. 같은 이름의 로컬 시트로 임의 연결하지 않는다. 두 피벗이 공유하는 캐시에서 하나만 원본을 변경해도 다른 피벗의 캐시·JSON·Undo를 보존한다. 레코드 없는 saveData=false 외부 피벗은 원본 출력·위치·항목·정의만 보존하고, 재계산에 필요한 원본 없이 필터·정렬·새로 고침을 하지 않는다. 이 파일의 필터 화살표 누락은 남은 UI 한계다. 레코드 없는 배치의 필드·질의·classic/blankRows/subtotalTop/repeatLabels/missingItems 변경은 오래된 항목 배치를 저장하지 않도록 거절한다. 명시적 외부 원본에 저장 레코드가 있고 refreshOnOpen이면 저장 캐시를 수용하지만, 외부 관계 없는 누락 로컬 원본의 refreshOnOpen은 기존 reader 제약으로 레코드를 수용하지 않는다.

- 초기 저장 화면 보존 경로는 가져온 위치·유효한 snapshot·새로 고침 옵션·원본/질의/캐시 바인딩·상대 영역을 함께 검증한다. 원본 본문·병합·폭·조건부 서식을 다시 쓰지 않고 머리글/보고서 필터 표시만 준비하며, 보존 후보의 초기 집계도 건너뛴다. 사용자가 필터/필드/원본을 바꾸면 기존 겹침 사전 검사와 실제 계산을 수행한다. 첫 변경 때 이전 본문의 셀과 블록 tail을 함께 정리하고 사용자 여백은 보존한다.
- XLSX 저장에서도 location과 rowItems/colItems를 한 묶음으로 보존한다. 축/Σ/값 순서와 타입·특수 항목까지 포함한 field.items 순번이 일치하는 경우에만 원문 배치를 사용한다. 캐시 번호만 바뀌어도 의미 순서가 같으면 허용하고, 순번이 바뀌면 세 배치 모두 현재 계산 경로로 처리한다. 표 전체 이동은 허용하지만 본문/필터 사이의 구조 삽입으로 상대 영역이 달라지면 보존하지 않는다.

## 성능 측정의 범위

같은 102MB 검체의 Node 파서 기준은 수정 전 172.2초·관측 최고 RSS 3.73GB, 개선 후 163.9초·1.05GB였다. 메모리는 약72% 감소했으며 시간 개선은 약5%다. 이는 Node의 파서 관측값이며 Safari 메모리 또는 사용자 화면 열기 시간을 뜻하지 않는다. 별도 전체 Workbook 준비 검사는 160.4초·최고1.14GB였다.

수식 약517만 개가 들어 있는 검체02는 전체 Workbook 준비 116.5초·최고2.85GB였으며 모델 GC 후에도 heap1.83GB였다. 파일 압축 용량만으로 기기의 편집 가능성을 판단할 수 없다. 이 개선으로 모든 크기의 파일을 모든 iPad에서 열 수 있다고 보증하지 않는다. 물리 iPad 모델·iPadOS 및 실제 Safari 검증은 아직 확보하지 않았다.

합성 백만 행·59개 반복 캐시 열의 보관 배열은 483KB였고, 백만 서식 빈 셀의 행 삽입 및 Undo/Redo 세 차례는 약0.57초였다. 이는 해당 구조의 합성 실험이며 모든 업무 파일의 편집 속도로 일반화하지 않는다.

## Excel 화면과 비교한 범위

실제 Excel을 별도 읽기 전용 인스턴스로 열어 검체06·07·11의15시트,580개 셀,83개 도면을 조사했다. 기존 사용자 Excel은 건드리지 않고 링크 새로 고침·계산·저장을 하지 않았다. pt→CSS px 변환과 직접 서식/앵커를 비교했으며 전체 화면 픽셀 동등 검사는 아니다.

- Excel 테두리는 병합·이웃 셀의 선을 투영하여 반환한다. WIXEL의 직접 저장 테두리와 raw COM 속성 차이만으로 선이 사라졌다고 판정하지 않는다.
- Windows192DPI의 Arial10 숫자 폭과 브라우저 모델의 폭 측정 차이, 자동 행 높이, 글꼴 대체가 남는다. 브라우저 배율에 따라 달라지는 DPR을 원본 좌표에 곱하는 임의 수정은 하지 않는다.
- 숫자 서식65개 차이를 조사했다.38개는 escape/quote/색 이름,21개는 통화 코드의 기본 표현,6개는 날짜 구분자의 시스템 locale 차이였다. m/d가 한국어 Excel에서 m-d로 표시되는 locale 차이를 모든 slash에 강제 적용하지 않는다.
- VML 주석 말풍선25개는 셀 주석·표시 상태로 보존되지만 말풍선의 원래 도형 위치까지 구현한 것은 아니다.
