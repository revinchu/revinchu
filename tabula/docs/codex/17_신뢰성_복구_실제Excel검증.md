작성: 2026-10-01. 작업 브랜치 `codex/wixel-production-readiness`.

## 실제 Excel 검증 도구

Windows에 설치된 Excel `16.0 / build 14334`를 별도 숨김 COM 인스턴스로 사용했다.
매크로·이벤트·외부 링크 갱신을 끄며, 일반 열기에 실패한 파일을 자동 복구하여 통과시키지 않는다.
기존에 사용자가 열어 둔 Excel 인스턴스나 업무 문서는 수정하지 않는다.

```powershell
node tools/excel-fixtures.mjs D:/Codex/Temp/wixel-production-excel
& tools/excel-interop.ps1 -FixtureRoot D:/Codex/Temp/wixel-production-excel
node tools/excel-roundtrip.mjs D:/Codex/Temp/wixel-production-excel
```

생성기에는 현대 차트 8종, 표면/등고선 4종, 보조 원형/막대 2종, 거래량 주식 2종, 그림 효과, 날짜 체계 2종, 표를 포함한 합성 파일 20개가 있다.
결과는 지정 폴더의 `synthetic-fixtures.json`, `excel-saved/results.json`에 저장한다.
현재 20개 일반 열기·차트 종류·개체 크기·셀 값·날짜 메타·재저장 검사, WIXEL 재열기 40개 검사를 통과했다.
Excel에서 제목·계열 색·축 최솟값·종류를 변경한 별도 합성 파일도 native 값 우선 읽기를 확인했다.
추가로 `tools/excel-chart-gallery.mjs`의 차트 갤러리 61개를 검증했다. OpenXML SDK 패키지 검사 61개, 실제 Excel 열기·재저장 61개, 다시 WIXEL로 읽기 61개가 모두 통과했다. 종류·누적·3D·분리량·표면 세부 종류·계열 값/이름·거품 X/Y/크기·콤보 계열별 종류/좌우 축을 비교했다. 이 과정에서 거품 크기/두 번째 Y 참조, 3D 꺾은선의 세 번째 축, 분리형 원형 저장, Excel에서 다시 저장한 분산형/방사형의 선·표식 상태를 수정했다.

이는 모든 Excel 버전, 모든 차트 조합, 실제 업무 파일의 무손실 보증이 아니다.

날짜 검증에는 Excel에서 생성한 1900/1904 XLSX 및 XLSB 파일을 사용했다. 일련번호, 날짜 수식, 경과시간, 일반 숫자를 분리하여 비교한다.
국가/OS 설정에 따른 날짜 구분자 치환은 별도 호환 영역이다.

## 서버 복구 계약

서버의 과거본은 현재 문서 용량 한도와 별도인 총 100MiB 범위에서 오래된 순으로 정리한다.
온라인 문서를 삭제하면 해당 과거본도 삭제된다. 공개 게시본은 이력을 쌓지 않는다.

백업 복원은 목록을 준비하고 문서를 임시 청크로 전송한 뒤, 모든 revision을 다시 확인하여 한 트랜잭션으로 적용한다.
중간 네트워크/검증/SQL 오류에는 기존 현재 문서를 유지한다. 임시 업로드에는 30분 만료가 있다.
현재 문서와 같은 이름을 복원하면 화면의 기존 문서는 브라우저 사본으로 유지하여 자동 저장이 복원본을 덮어쓰지 못하게 한다.
최종 응답을 잃은 경우에는 결과 불명으로 표시하고 자동 반복하지 않는다.
Node 서버에는 지원 capability가 없으면 이 메뉴를 제공하지 않는다.
현재 화면의 복구 사본 보관이 실패하면 버전 복원을 중단한다. 온라인 작업 중 다른 문서로 이동한 경우 응답이 새 화면을 덮어쓰지 않으며, 새 문서의 보류된 자동 저장도 다시 예약한다.

대용량 브라우저 저장은 세대별 시트/열 블록을 모두 완성한 뒤 작은 저장 목록을 CAS로 교체한다. Web Locks로 읽기·쓰기·정리를 함께 보호한다. Web Locks 미지원 환경에서는 안전을 위해 이전 세대 삭제를 보류하여 용량이 더 필요할 수 있다. GC는 새 v3 세대만 대상으로 하며 구버전 탭과의 경쟁을 피하기 위해 v2 시트·청크는 보존한다. v3 저장 목록은 예전 앱에서 읽을 수 없으므로 이전 프런트엔드로의 단순 롤백은 대용량 복원 호환성을 보장하지 않는다.
고장 주입 16개에는 시트/저장 목록 쓰기 실패, 강제 탭 종료, 저장 중 편집·문서 교체, 마지막 시점 편집, 직접 배율 변경, localStorage 실패, CAS 충돌, 자동 재시도, v1/v2 호환을 포함한다.

## 보관함 실패·충돌 보호

보관 문서 본문·버전·목록·만료본 삭제를 하나의 IndexedDB 트랜잭션으로 묶었다. 이전에는 목록 쓰기가 실패해도 본문만 새 값으로 바뀔 수 있었다.
두 탭의 읽은 revision을 비교하며, 앱을 다시 시작하여 관측 정보가 없을 때도 기존 본문과 동일하다고 확인하지 못하면 덮어쓰지 않는다.
이때 현재 편집 내용은 새 문서 ID의 보관 사본으로 한 번만 저장하고 한국어로 알린다. 사본 저장까지 실패하면 현재 내용·기존 원본·포인터를 유지한다. 사본 저장 중 새 편집이 생기면 오래된 사본의 ID를 현재 문서에 붙이지 않는다.

실제 브라우저 IDB 60개 검사와 source/compiled 각각 화면 25개 검사를 통과했다. 저장·삭제 중 용량 오류/트랜잭션 중단, 동시 목록 수정, 오래된 탭의 저장·삭제·과거본 복원, 같은 밀리초 이력, 고정 문서와 이름 붙인 이력의 보존을 포함한다.
`tools/library-atomic.mjs`는 소스 서버 전용, `tools/library-recovery.mjs`는 앱 화면 흐름 검사다.

## 큰 범위 성능 측정

같은 i5-9400F PC의 Chromium 151에서 CPU 4배 제한을 적용해, 합성 20만 셀로 수정 전/후 각각 한 번 측정했다. 실제 장비·브라우저·파일 내용에 따라 달라지며 제품 SLA가 아니다.

| 조작 | 수정 전 | 수정 후 |
|---|---:|---:|
| 필터 만들기 | 10,245.7ms | 305.1ms |
| 필터 항목 목록 열기 | 11,079.3ms | 158.5ms |
| 필터 적용 | 19,444.6ms | 590.9ms |

ARIA 격자의 선택 이동 측정 중앙값은 같은 비교에서 33.6ms → 14.3ms였다. 매번 DOM을 다시 만들던 경로를 재사용하도록 바꿨다.
5천·5만·20만 셀의 입력·복사/붙여넣기·스크롤·필터·직렬화·다시 열기 시나리오에서 자료 유실과 브라우저 예외는 없었다.
수정 후에도 20만 셀의 JSON 직렬화 911.7ms, 다시 열기 1,601.7ms와 일부 긴 메인 스레드 작업이 남았다. 더 큰 업무 파일과 저사양 장치 최적화는 계속 필요한 영역이다.

## 출시 판단에서 남는 항목

- 실제 업무 XLSX/XLSB 파일군에 대한 before/after 값·레이아웃 비교. 사용자 파일은 저장소와 전달 ZIP에 넣지 않는다.
- Excel 365 최신 확인란, OS별 글꼴/인쇄/PDF, NVDA 및 실제 한글 IME의 수동 검증.
- VBA 실행, Power Query/Power Pivot/DAX 전체 엔진, 외부 데이터 연결, 피벗 계산 항목의 일반 수식/해결 순서는 아직 동등하지 않다.
- Google Sheets 비공개 OAuth 연동, 셀 단위 실시간 공동편집, 조직 계정·역할·감사·관리자 복구·기기별 접근 회수는 별도 구현 영역이다.
- 개인 보관함 복구키는 전체 접근 권한이다. 새 버전 기록은 로그인/권한 체계나 종단간 암호화를 대신하지 않는다.
- 장기간 운영 부하·장애 복구 훈련·유료 제품의 지원 정책과 SLA는 자동 단위 테스트로 증명할 수 없다.
