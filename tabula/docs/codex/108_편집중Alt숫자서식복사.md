# 편집 중 Alt 숫자 서식 복사

셀이나 수식 입력줄을 편집한 상태에서 빠른 실행 도구 모음의 서식 복사 단축키를 누르면 동작하지 않던 경로를 수정한다. 기본 순서의 서식 복사는 `Alt+1`이며, 사용자가 순서를 바꾸면 현재 도구 모음에 표시되는 숫자를 따른다.

## 원인과 변경

마우스 서식 복사는 `run('painter')`에서 작성 중인 입력을 `commitEdit()`로 확정한 뒤 선택한 원본 셀의 서식을 보관한다. 기존 키보드 경로는 `editing` 상태를 만나면 리본 키 처리 전에 반환하며, `onEditingKey()`에는 빠른 실행 숫자를 전달하는 경로가 없었다. 일반 선택 상태의 서식 복사는 이미 작동했지만, F2 편집·새 값 입력 후 확정 전·수식 입력줄 편집에서는 마우스와 차이가 생겼다.

`app.js`의 `handleEditingQatKey()`를 문서 캡처 키 처리에 연결한다. 셀 편집기와 수식 입력줄에서만 Alt 시작과 빠른 실행 숫자를 기존 키팁 처리로 전달한다. Alt를 누르는 것만으로 입력을 확정하지 않으며, 숫자로 명령을 선택하면 기존 `activateKeytip()`과 `run()` 경로가 입력 확정·수식 구문 검사·데이터 유효성 검사·보호 검사를 수행한다. 별도의 서식 복사나 셀 변경 구현을 만들지 않는다.

- Alt를 누른 채 숫자를 누르는 방식과 Alt를 눌렀다 떼고 숫자를 누르는 방식을 모두 지원한다. 자동 반복 키는 기존 키팁 반복 방지 규칙을 따른다.
- 잘못된 수식이나 중지 형식의 데이터 유효성 제한을 만나면 마우스와 같은 안내 창을 열고 서식 복사를 시작하지 않는다. 원본 입력값과 대상 셀의 서식도 변경하지 않는다.
- Alt+Enter와 일반 입력은 키팁을 끝낸 뒤 편집기에 전달한다. Alt+Enter 줄바꿈을 빠른 실행 명령으로 처리하지 않는다.
- 실제 조합 중인 IME, Ctrl·Meta·AltGraph 조합은 편집을 확정하지 않는다. 검색창·다른 입력칸·대화상자·메뉴·파일 화면에는 이 편집 중 경로를 적용하지 않는다.
- 단일 서식 복사는 한 번 적용한 뒤 종료하고, 대상의 값·수식·메모와 다른 시트를 보존한다. 서식 적용은 기존 한 번의 Undo/Redo 단계이며, 작성 중인 값의 확정 이력과 구별한다. 리본을 두 번 클릭하는 연속 서식 복사도 기존 동작을 유지한다.

계산·피벗·파일 입출력 코어와 문서 저장 형식은 변경하지 않는다. 실제 고객 파일을 새로 열거나 수정할 필요가 없는 키보드 경로 수정이며, 검증은 합성 문서만 사용한다.

## 수정 전 재현

기준 커밋은 `1032408`이다. 같은 소스 서버에서 해당 커밋의 `app.js`만 응답 교체하여 현재 검증 도구로 수정 전 경로를 재현했다.

| 검사 | 수정 전 결과 |
|---|---|
| Chromium 초기 전체 검사 | 24개 중 16개 통과·8개 실패. 편집 중 Alt 실행 6개와 잘못된 수식·중지 유효성 검사에서 Alt 명령이 실행되지 않아 기대 안내가 나타나지 않은 2개다. |
| Chromium 보완 전체 검사 | 28개 중 20개 통과·같은 8개 실패. 추가한 줄바꿈·일반 입력·검색창 격리·실제 조합 중 입력 보존은 수정 전에도 통과했다. |
| Chromium 편집 경로 | F2·새 값 입력·수식 입력줄의 마우스 서식 복사 3개는 통과, Alt 누름 유지·순차 입력 6개는 실패했다. |
| WebKit 편집 경로 | 진단을 분류한 재실행에서 마우스 3개 통과·Alt 6개 실패로 같은 차이를 확인했다. 초기 하네스 실패 기록은 비공개 결과 폴더에 보존한다. |

초기 WebKit 9개 검사에서는 기존 viewport 설정의 `interactive-widget` 미지원 메시지가 `console.error`로 기록되어, 기능 단언을 통과한 마우스 3개도 마지막 오류 검사에서 실패했다. 도구는 이 정확한 안내 문구만 별도 `diagnostics` 배열에 보존하도록 보완했다. 다른 콘솔 오류와 페이지 실행 오류는 계속 실패로 처리한다. 같은 기준 커밋과 기능 검사로 재실행한 3개 통과·6개 실패를 기능 재현 결과로 사용하며, 초기 9개 실패 기록도 삭제하지 않는다.

## 회귀 도구와 검증 상태

`tools/qat-format-painter.mjs`는 새 브라우저 컨텍스트와 합성 문서에서 실제 Alt 키 입력·셀 클릭·서식·값·이력·입력 초점을 비교한다. `BROWSER=chromium|webkit`, `WIXEL_URL`, `QAT_OUT`, `QAT_TEST_FILTER`를 지원한다. `QAT_BASELINE_REF=1032408`은 수정 전 `app.js` 응답을 사용한다. 기본 검사는 숫자 열의 `Digit1`을 사용하며, 숫자 키패드나 물리 Windows·Apple 키보드 전체의 호환성을 이 결과로 단정하지 않는다.

2026-10-09에 다음 검증을 수행했다. 화면·이벤트·실패 로그 등 상세 증거는 Git에서 무시하는 D:의 `.local/qat-format-painter/`에 보관하며, 고객 파일·업무 값은 포함하지 않는다.

소스의 SHA-256은 `9850cd7234872c066163dee59f77b217fb3ec4ea011c9e2a69eeaee155be32e9`이며, 기존 회귀 도구 실행 전후와 실제 소스 서버 응답이 일치했다. `Process/229`·`Unidentified`·composition 입력은 합성 이벤트 검사이다. 물리 Windows 한글 IME·Apple 키보드·Native Excel을 직접 조작한 결과로 확대하지 않는다.

공개 주소는 [WIXEL 3](https://wixel-3.wizx.workers.dev/)이며, 배포 버전은 `a2742011-3688-4928-901e-33bf2ce6515e`이다. 실제 공개 HTML의 HTTP 200과 `wixel-4a3b6451c87b60d2.js` 참조를 확인했다. 공개 자산은 5,950,591바이트이며 SHA-256 `4a3b6451c87b60d2338ea78398fd6fb8ab75c3647286c170e70e35ab1eb8da6d`가 최종 로컬 번들과 일치했다.

공개 Chromium·WebKit의 합성 검사도 각각 30/30이 통과했다. 새 브라우저 컨텍스트에서 실제 공개 자산을 읽고, API 응답은 합성 상태 확인만 제공하며 외부 쓰기를 차단했다. 사용자 브라우저·원본 파일·개인 보관함은 사용하지 않았다. WebKit의 기존 viewport 미지원 안내는 별도 진단으로 보존했으며, 기능 실패·브라우저 실행 오류·외부 쓰기는 두 엔진 모두 0이다. 생성한 브라우저와 작업용 로컬 서버는 검증 후 종료했다.
